# 業務管理システム

チームの業務を一元管理するための汎用Webアプリ（業務管理フレームワーク）です。
**タスク / 定型・定期業務 / スキル・業務（タスクの完了からのスキルの自動更新・AIの分析と相談を含む） / 出勤表（勤務・年休）** をここで管理し、メールやチャットでの連絡を最小化することを目指します。

- **技術**: Python 3.9 + Flask + SQLite3（Flask-SQLAlchemy / Flask-Login / Jinja2 / Bootstrap 5）
- **想定環境**: サーバーで常駐起動し、メンバーの PC からブラウザでアクセス
- **規模**: 小規模チーム向け（SQLite で十分な規模を想定）

## 主な機能

| 機能 | 概要 |
|------|------|
| **タスク管理** | 登録（マネージャーのみ）／一覧・絞り込み／詳細／編集／ステータス更新／削除。複数担当・開始日/期限・**規模（負荷の目安）**・**進捗状況**の記載・**成果（定量/定性）** に対応。完了にするには成果（実績）の入力が必要。開始日は期限と同じ日か前の日付だけ。開始日・期限に日付として読めない値（ブラウザによっては年を6桁まで入力できます）・2000〜2099年の外の日付が送られたときは、空（未設定）として保存せず「開始日・期限は YYYY-MM-DD の実在する日付（2000年〜2099年）で入力してください」と表示します（今の期限は消えません）。以前の版で保存した2000〜2099年の外の日付のタスクは、日付を変えなければそのまま保存でき、編集画面の日付の欄もその日付まで選べます（ブラウザの入力チェックでほかの項目まで保存できなくならないように）。メンバーは計画系項目（優先度/日付/規模/担当者）を変更不可。一覧のキーワード検索は200文字まで（超えた分は使わず、その旨を表示）。編集画面を開いた後に、ほかの操作（担当者の完了の登録・マネージャーの変更など）で変わった項目は、古い画面の保存で上書きしません（保存せずに「同時に変更された項目」を表示し、変わった項目を今の内容にした画面を出します）。タスク・定型業務を削除すると、その番号が次に登録したものに使われることがありますが、開いたままの画面のボタン（編集・状態の変更・進捗の記載・削除）や期限超過通知のリンクが、新しい別のタスク・業務を操作・表示することはありません（「削除されています」と表示、リンクは 404）。ただし、以前の版が送った期限超過通知のメールのリンク（`/tasks/<番号>` だけで、印 `?t=` が付いていないもの）は確かめられないため、同じ番号の新しいタスクが開くことがあります。同時に押された削除・状態の変更（二度押し・2人が同時に操作）も内部エラーにせず、順番に処理します。登録・進捗の記載のボタンの二度押し（同じ画面からの同じ内容の送信）は1件だけ登録し、2回目は「2回目は登録していません」と表示します（戻って内容を書き直した送信は登録します）。空白・改行だけの進捗の記載は「進捗状況の内容を入力してください。」と表示します。進捗の記載の変更も、画面を開いた後にほかの操作（記載者本人の別のタブ・マネージャー）で変わっていたときは、古い画面の内容で上書きしません（保存せずに「ほかの操作でこの内容が変更されていた」と表示）。一覧の状態の選択・詳細の「状態を更新」（ワンクリックの状態の変更）も、画面を開いた後にほかの操作で状態が変わっていたときは変更せず、「ほかの操作で状態が「完了」に変更されています（変更していません）」のように今の状態を表示します（古い一覧から、完了にしたタスクを保留などに戻さないように）。今と同じ状態を選んで押したとき（選択を変えずに「状態を更新」を押した・二度押しの2回目など）は何も変えず（状態の変更の記録・最終更新も変えない）、「ステータスは既に「未着手」です（変更していません）。」と表示します。担当者が無効化されたタスクは、一覧・詳細・ガント・週報の担当者に「［無効］」を付けます。一覧・ガントの担当者の絞り込みでは、選んでいる無効化した担当者と、マネージャーには未完了のタスクが残っている無効化した担当者も「［無効］」を付けて選べます（担当の付け替えのため。選んでいる人が選択肢から消えて「すべて」と表示されたまま絞り込まれることはありません）。ガントの「「完了」を非表示」でも、完了にした後に戻したタスクの棒に完了の色の区間があるときは、凡例に「完了」を表示します。登録・編集の画面では **必要スキル（複数。担当者に必要な到達度 Lv1〜3）** を登録でき、スキルの到達度・出勤表（年休・勤務表）・**担当者の今の負荷とこのタスクの規模** から **推奨の担当者** を表示します。**規模が開始日〜期限の出勤日数を超える** ときは、登録・保存の前に案内します。登録の画面に **メールのファイル（Outlook の .msg・.eml）をドロップすると、AI が件名・本文から下書き（規模を含む）** を入れます（詳しくは「[タスクの登録の支援](#タスクの登録の支援必要スキル推奨の担当者規模の確認メールから下書き)」）。 |
| **定型・定期業務** | 各自の繰り返し業務を管理（担当者/業務名/目的/回数/頻度/1回所要/内容/手順書状況）。頻度の単位は **日・週・月・期（半期＝6か月）・年**（月間工数は 30日/月・4週/月・期は6か月・年は12か月で換算）。**担当者は複数選べます**（マネージャーが選びます。メンバーが登録すると自分が担当者になり、担当者の1人なら編集できます。担当者の変更はマネージャー）。全員が登録できます（メンバーは自分が担当のものだけを登録・編集。マネージャーはすべてを登録・編集）。削除はマネージャーのみ。ヒト別の件数・月間工数・手順書進捗のサマリー表つき（複数担当の業務は担当者ごとに1件と数え、月間工数は人数で均等に分けて計上。合計の行は業務の数。マネージャーダッシュボードの負荷も同じく均等割り）。編集画面を開いた後にほかの操作で変わった項目は、タスクと同じく古い画面の保存で上書きしません。登録の二度押しは1件だけ登録します。担当者が無効化された業務は、一覧・詳細に「［無効］」を付けます（一覧の担当者の絞り込みでも、選んでいる無効化した担当者と、マネージャーには業務が残っている無効化した担当者を「［無効］」を付けて選べます）。業務ごとに **リマインド**（実施日〔毎営業日・毎週・毎月・指定日〕に担当者へメールで知らせ、完了の入力があるまで1日2回リマインド）を設定でき、一覧の「未完了の定型業務」・詳細・ダッシュボードの「今日の定型業務」で完了を入力します。詳しくは「[定型・定期業務のリマインド](#定型定期業務のリマインドメール)」。 |
| **スキル・業務** | スキルマップ（テクニカル/コンセプチュアル/ヒューマンの3区分。到達尺度は全区分共通の **Lv0 未習得／Lv1 先輩と一緒にできる／Lv2 単独でできる（自立）／Lv3 教えることができる（自律）**）。上部に **AIの分析コメント・AIへの相談（チャット）・計画とメモ・最近の自動更新**。横軸に **ヒト（到達度）** と **業務（必要スキル・レベル）** を任意に表示。別ビューで **業務×ヒトの対応可否表**、メンバー個別画面に **育成計画（業務対応に必要なスキルの過不足）**。マネージャーのみ。スキル項目の編集画面を開いた後にほかの操作（別のタブ・別のマネージャー）で変わった項目（説明など）は、古い画面の保存で上書きしません（タスクと同じく「同時に変更された項目」を表示）。業務項目の一覧の保存でも、画面を開いた後にほかの操作で変わった項目は今の内容のままにします（ほかの項目は保存して、その旨を表示）。業務の必要スキルの保存は、ほぼ同時に届いたほかの保存とも重ならないように順番に処理します（後の側は上書きせず、その旨を表示）。スキル項目・業務項目の追加のボタンの二度押しは1件だけ追加します（業務項目の2回目は「既にあります」ではなく「2回目は登録していません」と表示）。スキルマップ・業務×ヒトの表を横にスクロールしても、1列目（スキル項目・業務の名前）と区分の見出しは左に残ります。 |
| **スキルの自動更新** | タスクを「完了」にすると、そのタスクに **進捗を記載したメンバー**（担当者かどうかではなく記載者）の記載から、AI がスキルの到達度を判定して上げます（根拠は本人の記載の引用・上げるだけ・1回の上げ幅は設定・取り消し可）。マネージャーの変更も含めて変更の履歴に残ります。詳しくは「[スキル](#スキル到達度-lv03自動更新aiの分析と相談)」。以前の版のスキルテストは削除しました。 |
| **出勤表・年休** | 出勤表（**横軸に日付、縦軸に勤務帯・勤務と人**。勤務の行に勤務表の記号、人の行に年休と休みの日。詳しくは「[出勤表と勤務](#出勤表と勤務シフト)」）。年休は承認なしの見える化。単日登録（全休/半休/時間休〔午前時間休・午後時間休。換算日数と同じ日に休む人数には数えません〕。**土日・祝日〔振替休日・国民の休日を含む〕は登録できません**。ただし勤務表で出勤の日は登録でき、勤務表で休日・年休の日は登録できません。以前の版で登録した土日・祝日の年休も、取得日を変えなければ種別の変更・取消はできます）、月カレンダー（土日色分け・同日上限の調整依頼。無効化したチームで絞り込んでいるときは、チームの選択肢に「［無効］」を付けて表示し、同日上限は判定しません〔絞り込まないカレンダー・登録の案内と同じく、無効化したチームは判定の対象外〕）、取消・編集は本人のみ（無効化したメンバーの年休はマネージャーも取消できます。マネージャーダッシュボードの「直近1か月の休暇予定」には無効化したメンバーの年休を出しません）。取消した年休の番号が次に登録した年休に使われても、開いたままの編集画面・取消のボタンが新しい年休を書き換え・取消することはありません（「画面を開いた後に、この年休は取消されています」と表示）。登録のボタンの二度押しは1件だけ登録し、2回目の画面にも「2回目は登録していません」と、同日の人数・今週の取得の案内を表示します。編集画面を開いた後にほかの操作（別のタブなど）で取得日・種別が変わっていたときは、古い画面の保存で上書きしません（タスクと同じく「同時に変更された項目」を表示し、変わった項目を今の内容にした画面を出します）。一覧の取得日の期間に日付として読めない値が指定されたときは、その条件を使わずにその旨を表示します（欄も空にします）。一覧の対象者の絞り込みで無効化した人を選んでいるときは、その人を「［無効］」を付けて表示します。 |
| **ダッシュボード（メンバーのトップ）** | メンバーがログインした後の画面（`/`。ナビの最初の項目「ダッシュボード」・アプリ名のリンク・「トップへ」もここ）。自分の担当タスク（期限超過・ステータス別の件数）、「今日の定型業務」、自分の担当分の活動状況・成果・ガントチャート。マネージャーのトップはマネージャーダッシュボードのため、マネージャーが `/` を開くとそちらへ移動します（個人ダッシュボードは表示しません）。 |
| **チーム管理** | チームマスタの追加/名称変更/有効無効、人×チームの紐づけ（兼務対応）、**メンバー（ユーザー）の追加・削除**。マネージャーのみ。固定ローカル管理者（`admin`）は、その環境のメンバーではないため、メンバーの表・紐づけの表に出しません（削除・無効化もできません。ログインを止めるには `ADMIN_PASSWORD` を変更。変更すると、既にログインしている admin のブラウザもログイン画面に戻ります）。人を指すフォーム（削除・復帰のボタン、紐づけの表、タスク・定型業務の担当者、到達度の編集）は「ユーザーID＋ログインID」で送り、画面を開いた後に削除・追加で同じIDが別の人に再利用されていたら保存しません（「画面を開き直して」と表示）。紐づけの保存で変わるのは、画面を開いたときに表に出ていた人とチームの組み合わせのうち、その画面でチェックを付けた・外したセルだけです（後から追加した人・チームの紐づけや、画面を開いた後にほかのマネージャー・別のタブで変えた紐づけは、古い画面の保存で戻りません）。チームの名称・並び順の保存でも、画面を開いた後にほかの操作で変わった項目は今の内容のままにし、その旨を表示します。メンバー・チームの追加のボタンの二度押しは1件だけ追加し、2回目は「2回目は登録していません」と表示します。既に復帰したメンバーを古い画面から「復帰」したときは「既に有効です（変更していません）」と表示します。業務データのあるメンバーの「削除」は無効化です（ログインできなくなり、担当者の選択肢・一覧から外れます。**担当中のタスク・定型業務は担当のまま残る**ため、必要なら担当を付け替えてください。チームの紐づけは外し、復帰しても戻らないため、復帰した後に「メンバーの紐づけ」で設定し直します）。無効化したメンバーのログインIDで追加しようとしたときは、そのメンバーを「無効化されたメンバー」の「復帰」で戻すよう案内します。チームが1つも無いときは、紐づけの表の代わりに「チームがまだありません」と案内します。メンバーの表で、各メンバーの **メールアドレス**（定型業務のリマインドの宛先）を変更できます。 |
| **マネージャーダッシュボード** | マネージャーがログインした後の画面（`/manager/`。ナビの最初の項目「マネージャーダッシュボード」・アプリ名のリンク・「トップへ」もここ。メンバーの「ダッシュボード」の代わり）。チーム俯瞰（タスク進捗/直近1か月の休暇予定/スキル保有状況/メンバー別 平均到達度〔有効なテクニカルスキルの平均。未評価のスキルは0として数える〕）、**ヒト別 負荷・案件状況**（タスク＋定型業務の月間工数を合算・余力表示）、メンバーの活動状況、**全タスクのガントチャート**（期間〔最長731日・約2年〕・担当者フィルタ・ステータス色分け・カミナリ線）。成果などの期間の日付の欄は、入力の途中で再読み込みしないよう「この期間で表示」ボタン（または Enter）で反映します（ダッシュボードの期間も同じ）。一番上に **エグゼクティブサマリー**（AI分析の①〜④のまとめと推奨アクションを1つの文章にまとめたもの。表示だけ。画面を切り替えずに見られ、「AIで分析」もここから実行できる）。**AI分析（サマリーと推奨アクション）**: タスクの進捗・スキル状況・成果物の状況・各人の能力をまとめ、いま対応することを優先度順に表示（「AIで分析」で AI がコメントなどの本文を読み、課題の抽出・コメントへの対応の判定・書き直し案・各人の所見を加える）。詳しくは「[AI分析](#ai分析サマリーと推奨アクション)」。 |
| **週報（自動作成・メール送信）** | タスク情報から「チーム全体＋1人1ページ」の週報を Word で作成し、毎週決まった曜日・時刻にメールで自動送信。画面から今すぐ作成（ダウンロード/テスト送信/本番送信）も可能。AI（ChatGPT互換API）で文章を整形（未設定ならルールベース）。マネージャーのみ（ナビの「定期メール」。設定は「システム設定」）。詳しくは「[週報](#週報自動作成メール送信)」。 |
| **期限超過通知（毎朝のメール）** | 営業日（土日・祝日以外）の毎朝、期限を過ぎた未完了タスクの一覧を1通のメールで自動送信。状態（未着手／進行中・保留）ごと・担当者ごとにまとめ、直近の進捗記載とタスクへのリンクを付ける。画面でプレビュー・テスト送信・今すぐ送信も可能。マネージャーのみ（ナビの「定期メール」。設定は「システム設定」）。詳しくは「[期限超過通知](#期限超過通知毎朝のメール)」。 |
| **定型・定期業務のリマインド（メール）** | 定型業務の実施日に担当者（と業務ごとの追加の宛先）へメールで知らせ、その回の完了の入力があるまで1日2回（既定 09:00・15:00）リマインド。宛先ごとに「本日実施予定」「【リマインド】未完了」を1通にまとめ、業務の画面・完了の入力へのリンクを付ける。各ユーザーのメールアドレスはユーザーメニューの「メールアドレス」（マネージャーはチーム管理でも）で登録。自動送信の設定・プレビュー・テスト送信は「システム設定」の「定型業務リマインド」タブ。詳しくは「[定型・定期業務のリマインド](#定型定期業務のリマインドメール)」。 |
| **Excel データ出力** | 各メニューの全データ（現在＋履歴。スキルの到達度の変更の記録を含む）を `.xlsx` で出力。マネージャーのみ。Excel に入れられない文字（改行・タブ以外の制御文字、U+FFFE/U+FFFF など）は除き、1つのセルの上限（32,767 文字）を超える値は上限までにして末尾に「…（以下省略…）」と書きます（全文はアプリの画面で確認。文字数は Excel と同じく、絵文字など一部の文字を2文字と数えます）。ログインの有効期限が切れた状態で「Excel出力」を押したときは、ログインの後にマネージャーダッシュボードを表示します（ファイルは自動では作らないため、もう一度「Excel出力」を押します）。 |
| **システム設定** | その環境の設定を1画面（タブ）で変更。**メールの宛先**（週報・期限超過通知の宛先）／**週報**／**期限超過通知**／**スキル（AI）**／**AI分析**／**定型業務リマインド**。マネージャーのみ。すべての環境で共通の基本設定（接続先・パスワードなど）は admin のシステム管理で変更。詳しくは「[システム設定](#システム設定)」。 |
| **システム管理（admin）** | 固定ローカル管理者（`admin`）だけの画面（`/admin/`。admin はログインの後にここを表示）。すべての環境（グループ）の一覧と「開く」（その環境のマネージャーと同じように編集）・**環境**（追加〔名前だけ〕・名前の変更・停止/再開）・**基本設定**（AI・メールの送信サーバー・差出人・送信を許可するドメイン・リンク・LDAP・admin のパスワードなど。初期値 `config.py` ＋ 画面の設定 `instance/settings.json`。メール・AI の接続テストつき）・**勤務パターン**（勤務・勤務表の記号・勤務表の入力。会社の中で共通）。詳しくは「[システム管理](#システム管理admin)」。 |
| **複数の環境（グループ）** | 1つのサーバーを、複数のグループ（マネージャーごとのチーム）で使い分ける。ログインの画面は1つで、ログインの後に自分が登録されている環境を選ぶ。環境ごとに DB（タスク・メンバー・スキル・出勤表など）と機能の設定・メールの宛先が別。環境の追加・停止は admin のシステム管理の「環境」。詳しくは「[複数の環境](#複数の環境グループ)」。 |

### 役割（ロール）

**マネージャー（`manager`） / メンバー（`member`）** の2種類。マネージャーが全機能（スキル〔AIの分析・相談を含む〕・各ダッシュボード・チーム管理・データ出力・定期メール〔週報・期限超過通知・定型業務リマインドの設定〕・システム設定を含む）を利用でき、メンバーは一般利用（タスク/定型業務/年休）が中心です。マネージャーはスキル管理の対象外です（スキルの自動更新の対象にもなりません）。

このほかに、アプリ全体の管理者として **固定ローカル管理者（`admin`）** がいます。admin は特定の環境のユーザーではなく、ログインの後は専用の「**システム管理**」の画面（`/admin/`）を表示します。すべての環境で共通の設定（**基本設定**・**勤務パターン**）と **環境** の追加・停止を変えられるのは admin だけで、admin はすべての環境を開いて、その環境のマネージャーと同じように編集できます。各環境のマネージャーは、今までどおりその環境の中（タスク・定型業務・スキル・チーム・出勤表の年休・定期メールの設定・メールの宛先など）を編集します（「[システム管理](#システム管理admin)」）。

ナビの最初の項目は、メンバーは「ダッシュボード」（個人ダッシュボード）、マネージャーは「**マネージャーダッシュボード**」です（マネージャーのトップ。ログインした後・アプリ名のリンク・「トップへ」もここに着き、`/` を開いてもここへ移動します）。マネージャーのナビは、スキル・チーム管理・システム設定を「**管理**」にまとめています（項目が多いため。幅 1200px 未満の画面ではメニューのボタンで開きます）。admin が環境を開いているときは、ナビに「**システム管理**」（システム管理の画面に戻る）を表示します。

## セットアップ

```bash
# 1.（推奨）仮想環境
python -m venv .venv
.venv\Scripts\activate        # Windows
# source .venv/bin/activate   # Linux/Mac

# 2. 依存パッケージ
pip install -r requirements.txt

# 3. 初期データ（ダミーユーザー・サンプルデータ）の投入
flask --app app seed
```

- `flask` コマンドは **`app.py` のあるフォルダで実行** します（`--app app` は、今いるフォルダの `app.py` を指します）。`flask` が見つからない場合は、仮想環境を有効にするか、`python -m flask --app app ...` の形で実行します。
- 環境ごとの設定（接続先・宛先・パスワードなど）は、リポジトリに同梱の **`config.py`（初期値）** と、システム管理の「基本設定」（admin）で保存する **`instance/settings.json`（画面の設定。初期値より優先）** の2つから決まります（「[設定](#設定初期値-configpy-と画面の設定-instancesettingsjson)」）。同梱の `config.py` の値はすべて空（ポートとタイムアウトだけ 25・60）なので、導入後に admin でログインし、システム管理の「基本設定」で接続先・admin のパスワードを、各環境のシステム設定の「メールの宛先」タブで宛先を設定してください。
- 初回の起動（`seed` を含む）で、セッションの秘密鍵 `SECRET_KEY` が `config.py` にも画面の設定にも無ければ、1回だけ生成して `instance/settings.json` に保存します（再起動しても同じ鍵）。保存できなかったとき（フォルダの書き込みの権限が無い・ディスクの空きが無いなど）は、起動のたびに別の鍵にはせず、「SECRET_KEY が未設定のため鍵を生成しましたが、instance/settings.json に保存できませんでした（…）」と表示して止まります。
- 旧版（環境ごとの設定を `instance/config.py` に書いていた版）から更新したときは、`flask --app app import-old-config` でその値を `instance/settings.json` に取り込みます（「[以前の版からの更新](#以前の版からの更新)」）。

## 起動

```bash
# このPCだけで使う（ブラウザで http://127.0.0.1:8050 を開く）
flask --app app run --port 8050

# 同じネットワーク（LAN）の他の PC からも使う（サーバーでの通常の起動）
flask --app app run --host 0.0.0.0 --port 8050
```

- メンバーは `http://（サーバーのIPアドレス）:8050` でアクセスします（初めて LAN に公開するときは、Windows のファイアウォールでの許可が必要な場合があります）。
- 待ち受けのアドレス・ポートは **起動のコマンドの `--host` / `--port` だけ** で決まります。`--host` を省略すると `127.0.0.1`（このPCだけ）、`--port` を省略すると `5000` です。
- 止めるときは Ctrl+C です。
- 運用の記録（基本設定の変更〔項目とユーザー名。値は書きません〕、`SECRET_KEY` の自動生成、自動送信の結果、同じフォルダのほかのサーバーで自動送信のスケジューラが動いているため待機していることなど）は、`--debug` なしの通常の起動でも、起動した画面に `INFO in app: …` の行として表示されます。
- **定期メール（週報・期限超過通知・定型業務リマインド）の自動送信は、`flask --app app run` で起動している間だけ** 動きます（起動時に「定期メール（週報・期限超過通知・定型業務リマインド）の自動送信スケジューラを起動しました。」と表示）。`seed` / `migrate` コマンドでは動きません。同じフォルダで2つ以上起動しても、自動送信を行うのは1つのプロセスだけです（`instance/scheduler.lock` のロック）。ロックを持っているプロセスが止まると、残っているサーバーが約30秒以内にロックを取り直して自動送信を引き継ぎます（同じ日時の二重送信はしません）。どのプロセスでも自動送信が動いていないときは、週報・期限超過通知の画面の「次回の自動送信」と、システム設定の「定型業務リマインド」タブに「自動送信のスケジューラが動いていません」と表示します。自動送信の実行の印（各機能の設定ファイルの `last_auto_key` / `auto_slots`）を書けなかったとき（Windows で、同じフォルダのほかのサーバーやバックアップ・ウイルス対策のソフトなどがそのファイルを開いていた）は、少し待って書き直し、それでも書けなければその回は実行せずに前回の結果に残し、同じ分のうちにもう一度試します（二重には送りません）。印を記録したら、実行の前に各機能の「前回の結果」に「自動送信を開始しました（…の分）。完了の記録がありません…」を書いておき、実行が終われば本当の結果で上書きします。処理の途中でサーバーが停止・再起動したとき（週報の AI の作成中など）も、その分を実行しなかったことが「前回の結果」で分かります（印は残るため、その分は自動では送り直しません。必要なら画面の「今すぐ…」で送ってください）。システム管理の「基本設定」で保存した設定（`SECRET_KEY` 以外）は、同じフォルダのほかのサーバーにも、次の画面の表示の前と自動送信の前に反映されます（`instance/settings.json` の更新〔日時とサイズ〕を見て読み直します。`config.py` を直接編集した値は、すべてのサーバーの再起動で反映）。
- 起動時の `WARNING: This is a development server. ...` は、`flask run` で起動すると Flask が常に表示するメッセージです。

### 開発・動作確認（--debug）
```bash
flask --app app run --port 8050 --debug
```
- `--debug` を付けると、`app.py` などの `.py` ファイルを変更したときにサーバーが自動で再起動し、`templates.html` の変更も次の表示から反映されます。システム設定の画面で保存する値は `instance/settings.json`（Python のファイルではない）に書くため、保存で再起動することはありません（以前の `--exclude-patterns "*/instance/*"` は不要です）。
- `--debug` ではエラーの画面から Python のコードを実行できるデバッガーが有効になります。**自分の PC での開発用です。`--host 0.0.0.0` と一緒に使わないでください。**
- `--debug` のときは、2つのプロセスが動きます。最初に起動した **親のプロセス** はサーバーを起動し直すだけで（ファイルの変更の見張りも画面の表示もしません）、自動送信はこの親のプロセスで動きます。ファイルの変更の見張りと画面の表示は、親が起動した **サーバーのプロセス** が行い、ファイルが変わるとこのプロセスが終わって新しく起動し直されます。画面から保存した基本設定は自動送信の前に読み直して反映しますが、親のプロセスのコードは読み直されないため、コードの変更と直接編集した `config.py` を自動送信に反映するには、一度止めて起動し直してください。

### サーバーの起動時に自動で起動する
Windows の「タスク スケジューラ」でタスクを作り、「操作」を次のように設定します（「トリガー」は「コンピューターの起動時」など）。

| 項目 | 値 |
|------|------|
| プログラム/スクリプト | `flask.exe` の場所（仮想環境なら `（app.py のあるフォルダ）\.venv\Scripts\flask.exe`。それ以外はコマンド プロンプトで `where flask` を実行して確認） |
| 引数の追加 | `--app app run --host 0.0.0.0 --port 8050` |
| 開始（オプション） | `app.py` のあるフォルダ |

以前の版で `python serve.py`（または `waitress-serve ... --call app:create_app`）を登録していた場合は、この設定に置き換えてください（「[以前の版からの更新](#以前の版からの更新)」）。

## コマンド

どれも `app.py` のあるフォルダで実行します。

| コマンド | 内容 |
|------|------|
| `flask --app app run --port 8050`（LAN に公開するときは `--host 0.0.0.0` も） | サーバーとして起動（定期メールの自動送信もこのときだけ動く） |

| `flask --app app --help` | 使えるコマンドの一覧 |

## ログインと認証

ログインは **①LDAP（本人確認）→ ②アプリ登録チェック** の2段階です。

1. **本人確認**: プロジェクト直下の `ldap_client.py` の `authenticate()`（現状はダミー実装）。本番はこの関数内の「LDAP-API」ブロックを実 API に差し替えるだけで移行できます（「[本番LDAPへの移行](#本番ldapへの移行)」）。
2. **アプリ登録チェック**: LDAP で本人確認できても、**アプリに登録済み・有効なユーザーでなければログインを拒否**します。新しいメンバーはマネージャーが「チーム管理 → メンバーの管理」で登録してからログイン可能になります。

- ログインの状態（セッション）は「ユーザーID＋ログインID」で覚えます。業務データの無いメンバーを削除すると、そのユーザーIDは次に追加した人に再利用されることがありますが、削除した人のブラウザに残ったログインの状態が別の人として使われることはありません（ログイン画面に戻ります）。この形式にした版へ更新した後は、全員が一度だけログインし直します。
- **ログアウト・有効期限**: ログインのたびにランダムな印を作り、ブラウザのセッション（クッキー）と `instance/login_sessions.json`（Git 管理外。DB は使いません）に残して、画面を開くたびに照合します。**ログアウトすると、そのブラウザの印を消す** ため、ログアウトの前のクッキーを控えて別のブラウザ・別の PC から使っても、ログイン画面に戻ります。メンバーを無効化・削除したときは、その人のすべての印を消します（ログイン中のブラウザも次の操作でログイン画面に戻り、復帰しても前のクッキーは使えません）。**ログインしてから12時間** が過ぎると、ログインし直します（「ログインしてから12時間が過ぎたため、ログインし直してください。」と表示）。このファイルが無い・読めないときは、全員がログインし直します（ログインするとファイルを作り直します）。この仕組みを入れた版へ更新した後は、全員が一度だけログインし直します。
- **ログインの失敗の制限**: 同じ送信元（IP アドレス）から同じIDで10分の間に5回、または同じ送信元から（IDを問わず）30回パスワードを間違えると、その送信元からそのID（30回のときはすべてのID）のログインを10分間断ります（「ログインに続けて失敗したため、しばらくログインできません」と表示。パスワードの総当たりの防止）。同時に多くのログインが送られても、確かめている途中のログインを回数に含めて数えるため、パスワードを確かめるのは同じID・同じ送信元とも上限の回数（5回・30回）までです（上限に届いている間に送られたログインは、パスワードを確かめずに「ログインの確認が重なっているため、いまはログインできません」と表示）。回数はサーバーのメモリで数えるため、サーバーを再起動すると消えます。admin のログインの失敗と、制限を始めたことは、サーバーのログに残します（パスワードは残しません）。
- **ログイン中の画面はブラウザに残しません**: ログイン中の画面・Excel・Word の応答に `Cache-Control: no-store` を付けます（共用の PC で、前の人がログアウトした後に、ブラウザの「戻る」でマネージャーの画面などがキャッシュから表示されないように）。
- ログインした後は、メンバーはダッシュボード（`/`）、マネージャーはマネージャーダッシュボード（`/manager/`）、admin はシステム管理（`/admin/`）を表示します。ログインの前に開こうとしていた画面（`next`。このアプリの中の画面だけ）があれば、どちらもその画面を表示します。
- ログインの有効期限が切れた状態で保存・変更などのボタンを押した場合は、ログインの後、その操作の画面（上の階層の画面）に戻り、「直前の操作は行われていません」と表示します（もう一度操作してください）。
- 送信の内容が正しくない（400。古い画面・選択肢に無い値など）・権限の無い画面（403）・見つからないページ（404。削除されたタスクへのメールのリンクなど）・画面として開けない URL（405）・想定外のエラー（500。内容はサーバーのログに残ります）は、日本語の案内とトップへのボタンを表示します。
- 認証サーバー（本番の `ldap_client.py` が問い合わせる LDAP認証API）が止まっている・つながらないときは、内部エラーの画面ではなく、ログイン画面に「認証サーバーに接続できなかったため、ログインできませんでした」と表示します（例外の内容はサーバーのログに残します。パスワードはログに出しません）。`authenticate()` の結果の形が違う（辞書でない・ログインIDが無い）ときも同じ案内にします。結果に氏名（`display_name`）が無い・空のときは、登録済みの氏名のままにします（空の氏名で上書きしません）。
- 保存・変更などの操作は、このアプリの画面から送られたものだけを受け付けます。ブラウザが付ける送信元（`Origin`、無ければ `Referer`）が、このアプリと同じ「http/https・ホスト・ポート」でなければ保存せずに 403 にします（同じサーバーの別のポートで動くほかの Web サービスの画面からの送信も断ります）。開くだけで状態が変わる画面（ログアウト）も、ほかのサイト・別のポートの画面から開かれたときは何も行いません（ブラウザが付ける `Sec-Fetch-Site`、無ければ `Referer` で判断）。画像などとして読み込まれたと分かるとき（`Sec-Fetch-Dest`）は 403 にし、それ以外は「このアプリの画面から開いてください」と続けるためのボタン（ログアウトは POST のボタン）を表示します。ブラウザは https でも localhost でもない URL（LAN の `http://（サーバーのIPアドレス）:8050` など）には `Sec-Fetch-*` を付けず、https のサイト（Web 版のチャット・メールなど）のリンクや no-referrer のページから開かれたときは `Referer` も付けないため、どちらも無いブラウザの要求（`User-Agent` が `Mozilla/` で始まるもの）も、送り元が分からないものとして同じボタンの画面にします（アドレスを直接入力した・ブックマークから開いたときも、LAN の http ではボタンを1回押します。このアプリの画面のリンク・ボタンから開いたときは `Referer` で分かるため、今までどおりすぐに行います）。ブラウザ以外（テスト・コマンドなど）からの要求は今までどおりです。ほかのサイトの画面の中（iframe）には表示しません（`X-Frame-Options: SAMEORIGIN`）。
- 1回の送信（フォーム）は約50万バイト（日本語でおよそ5万字）までです。超えたときは入力が大きすぎる旨の画面を表示します（保存はされません。ブラウザの「戻る」で入力した画面に戻れます）。ファイルを含む送信や、大きさ（Content-Length）を付けない送信も、1回の要求は100万バイトまでです（`MAX_CONTENT_LENGTH`）。
- ログインした後に、別のタブに残っていたログイン画面を開いた・送信したときは、その画面の戻り先（`next`。このアプリの中の画面だけ）に移動します。ただし、ログイン中の人と別のIDを送ったとき（共用の PC で、前の人のログインが残った画面から別の人がログインしたなど）は、前の人のログインを終えてから（「○○ さんのログインを終了しました」と表示）、送られたID・パスワードを確かめます（正しければその人でログインし、誤っていればログアウトした状態でエラーを表示します。前の人のまま操作を続けることはありません）。
- 画面の JavaScript が使う呼び出し（「AIで下書き」・AI分析の実行中の確認）でログインの有効期限が切れていたときは、ログイン画面に移動せずに「ログインの有効期限が切れています」と表示します（AI分析の実行中の画面は再読み込みしてログイン画面へ）。
- **複数の環境（グループ）** で使っているときは、ログインの画面は1つで、ログインの後に有効なメンバーとして登録されている環境へ進みます（複数なら環境の選択の画面）。ログアウト・有効期限・パスワードの変更による再ログインは、すべての環境に効きます（「[複数の環境](#複数の環境グループ)」）。環境が1つのあいだは、上のとおり今までと同じです。
- Bootstrap・Bootstrap Icons は CDN（cdn.jsdelivr.net）から読み込み、公開されているハッシュ（`integrity`）と一致するときだけ使います（配信元や経路で書き換えられたファイルは読み込みません）。

### 固定ローカル管理者
LDAPとは独立に常に有効な管理者アカウントを1つ用意しています（初期設定・緊急用。本番でLDAPに差し替えても残ります）。

- admin は **このアプリ全体の管理者** です（特定の環境のユーザーではありません）。ログインの後は「**システム管理**」の画面（`/admin/`）を表示し、基本設定・環境・勤務パターンの変更（admin だけ）と、すべての環境を開いての編集ができます（「[システム管理](#システム管理admin)」）。システム管理を使えるのは、固定ローカルの認証（`ADMIN_PASSWORD`、空のときは `ldap_client.py` の固定パスワード）でログインした admin だけです（`ADMIN_PASSWORD` が空のときに `ldap_client.py` の LDAP の判定で入った、同じ ID のアカウントは使えません）。
- ID: `admin` / パスワード: 基本設定の `ADMIN_PASSWORD`（初期値 `config.py` または画面の設定 `instance/settings.json`。「[設定](#設定初期値-configpy-と画面の設定-instancesettingsjson)」）
- 同梱の `config.py` では `ADMIN_PASSWORD` は空です（下のとおり、空のあいだは `ldap_client.py` の判定で `admin` がログインできます。**同梱の `ldap_client.py` には `admin` 用の既定の固定パスワードがある** ため、新しく導入したサーバー・更新して `import-old-config` をまだ実行していないサーバーでは、その公開されているパスワードで `admin` がログインできる状態です）。導入後に **システム管理の「基本設定」** で設定してください（保存するとすぐに有効。`config.py` を直接編集した場合はサーバーの再起動で反映）。設定するまでは、起動のたびに「ADMIN_PASSWORD が未設定のため、admin のログイン可否は ldap_client.py の判定に任されています…」と1行表示し、基本設定の `ADMIN_PASSWORD` の欄にも同じ注意を表示します（アプリがパスワードを自動で決めることはありません）。
- `ADMIN_PASSWORD` を変更すると、既にログインしている admin のブラウザも次の操作でログイン画面に戻ります（漏れたパスワードを変えたときに、前のパスワードでログインしたままのブラウザが使えないように。ログインのときにパスワードの印〔`SECRET_KEY` で作る HMAC。パスワードそのものは含みません〕をセッションに残し、毎回今のパスワードと照合します。`ldap_client.py` の `_LOCAL_ACCOUNTS` の固定パスワードでログインした場合も同じ）。この版へ更新した後は、admin でログインしていたブラウザは一度だけログインし直します。ログイン画面には「admin のパスワードが変更されたため、ログインし直してください。」と表示します（保存などの送信だったときは「パスワードの変更の後にこのブラウザから送られた保存・変更は行っていません（パスワードの変更そのものは保存されています）」も表示し、ログインの後に「ログインの有効期限が切れていた」とは表示しません。基本設定の画面で自分のパスワードを変えて「基本設定を保存」を二度押ししたときも同じです）。
- この確認はログインの処理（`app.py` の「5-1. 認証」）で、`ldap_client.py` より先に行います。`ADMIN_PASSWORD` が設定されている間は、`admin` はこの値でだけログインできます。
- `ADMIN_PASSWORD` を空にすると、`admin` の確認も `ldap_client.py` の `authenticate()` に任せます（`ldap_client.py` に `admin` 用の固定パスワードがある場合は、それでログインできるようになります。同梱の `ldap_client.py` には既定の固定パスワードがあるため、**空にしても admin のログインは無効になりません**）。
- 旧版の `instance/config.py` に `ADMIN_PASSWORD` を書いていた場合は、`flask --app app import-old-config` で画面の設定に取り込めます（「[以前の版からの更新](#以前の版からの更新)」）。

## 設定（初期値 config.py と画面の設定 instance/settings.json）

環境によって変わる値（秘密鍵・管理者パスワード・LDAP / AI / メールの接続先など）は、次の **2つの層** から決まります。

| 層 | ファイル | 役割 |
|------|------|------|
| 初期値 | `config.py`（`app.py` と同じフォルダ。**Git 管理下**。リポジトリに同梱） | 環境ごとの設定の初期値。無いと起動しません |
| 画面の設定 | `instance/settings.json`（DB と同じフォルダ。**Git 管理外**） | システム管理の「基本設定」（admin）で保存した値。**初期値より優先** |

- **有効な値** = `instance/settings.json` にその項目があればその値（空でも）、無ければ `config.py` の値です。画面の「初期値に戻す」で項目を `settings.json` から外すと、`config.py` の値に戻ります。システム管理の「基本設定」には、項目ごとに「初期値（config.py）」「画面の設定」「有効な値」と、どちらの層が有効かを表示します（パスワード・キーは「設定あり／未設定」だけ）。
- **コードの中に既定値はありません**（「入力が無ければ○○を使う」はしません）。どちらの層にも無い・空の項目は「未設定」として扱います。AI は接続先（`AI_API_URL`）とモデル名（`AI_MODEL`）の両方が設定されるまで使いません（外部の既定の接続先に送ることはありません。各画面に「AIの接続先（AI_API_URL）とモデル名（AI_MODEL）をシステム管理の「基本設定」（admin）で設定してください」と表示）。メールは送信サーバー・ポート番号・差出人が揃うまで送りません（ポート番号も既定値 25 などに置き換えません）。
- **`config.py` は公開リポジトリに同梱**しています。同梱の値はすべて空（`MAIL_SMTP_PORT = 25`・`AI_TIMEOUT = 60` だけ値あり）です。**実際のパスワード・APIキー・メールアドレスを `config.py` に書いてコミットしないでください。** 実際の値は、サーバーの上でだけ `config.py` を書き換える（コミットしない）か、システム設定の画面で設定します。アプリが `config.py` を書き換えることはありません。
- `config.py` が無い・書式に誤り（引用符の閉じ忘れ・引用符の無い値など）があると、サーバー（`flask --app app run`）・`seed`・`migrate` は起動せずに `Error: 設定ファイル config.py がありません（…）` / `Error: 設定ファイル config.py の N 行目に誤りがあるため、読み込めません（…）` と表示して終わります（行の内容・設定値は表示しません）。コードの中の値で動くことはありません。`instance/settings.json` があるのに読み込めない（壊れている）ときも同じく起動せず、画面の表示中に壊れたときは基本設定の画面にその旨を表示して保存できなくします（上書きはしません）。
- **`SECRET_KEY`**（セッションの秘密鍵）は、どちらの層にも無ければ **起動時に1回だけ生成して `instance/settings.json` に保存** します（再起動しても同じ鍵。ログに値は書かず「SECRET_KEY が未設定のため生成し、instance/settings.json に保存しました」とだけ表示）。同じフォルダで2つのサーバー（`--debug` の親と子を含む）が同時に最初の起動をしても鍵は1つです（生成は `instance/settings.lock` のロックで直列にし、保存の後にファイルを読み直してファイルにある鍵を使います。先に生成したプロセスがあればその鍵を使い、生成の表示は出しません）。保存できないときは起動せずにその旨を表示します（起動のたびに別の鍵にはしません）。
- `instance/settings.json` の値の **型が項目に合わないとき**（数の `SECRET_KEY`、辞書の `MAIL_TO` など。手で編集したときに起こり得ます）は、使うときの内部エラー（500）にせず、読み込めないファイルとして項目の名前を表示して止めます（起動時は起動せず、表示中なら基本設定の画面に表示して保存できなくします。値は表示しません）。`config.py` の値も同じく起動時に確かめます（文字列の項目は `"..."`、アドレスの一覧は `[...]`、ポート番号・タイムアウトは整数。`60.0`・`"30"` のような整数として読める値は使えます）。
- **`ADMIN_PASSWORD`** が空のあいだは、`admin` の確認を `ldap_client.py` の `authenticate()` に任せます（「[固定ローカル管理者](#固定ローカル管理者)」）。
- **アプリは環境変数を読みません**（設定は上の2つの層だけで完結します）。ただし `flask` コマンドは、python-dotenv が入っていると `.env` を自動で読み込みます。以前の版の `.env` が残っている場合は、移動または削除してください（「[以前の版からの更新](#以前の版からの更新)」）。
- 旧版の `instance/config.py` は **読みません**。`flask --app app import-old-config` でその値を画面の設定に取り込めます（起動時に、取り込んでいない `instance/config.py` があると「旧版の instance/config.py があります。flask --app app import-old-config で取り込めます」と1行表示します）。
- 以前の版の次の項目は使わなくなりました。`config.py` に書かれていても動作には影響せず、システム管理の「基本設定」の「その他」に「**未使用**」と表示されます（不要なら `config.py` から消してください。`import-old-config` は取り込みません）。
  - `SERVER_HOST` / `SERVER_PORT`: 待ち受けのアドレス・ポートは起動のコマンドの `--host` / `--port` で指定します
  - `MAIL_USE_TLS` / `MAIL_USERNAME` / `MAIL_PASSWORD`: メールは暗号化（STARTTLS）・認証（ログイン）なしで送信します
  - `MAIL_TEST_TO`: テスト送信・メール接続テストは差出人（`MAIL_FROM`）宛てに送ります
  - `OVERDUE_MAIL_TO` / `OVERDUE_MAIL_CC`: 期限超過通知は週報と同じ `MAIL_TO` / `MAIL_CC` に送ります

| 項目 | 用途 | 同梱の config.py の初期値 |
|------|------|------|
| `SECRET_KEY` | セッション暗号化キー。どちらの層にも無ければ起動時に生成して `instance/settings.json` に保存 | 空 |
| `ADMIN_PASSWORD` | 固定ローカル管理者 `admin` のパスワード。空なら `admin` の確認は `ldap_client.py` に任せる | 空 |
| `LDAP_API_URL` | LDAP認証APIのURL（本番で使用） | 空 |
| `AI_API_URL` | ChatGPT互換（OpenAI互換の形式）APIのエンドポイント。既定の接続先は無く、ここで設定した接続先にだけ送る。週報の文章整形・スキルの説明の下書き・AI分析・スキルの自動更新・スキルマップのAI（分析・相談）・メールからのタスクの下書きに使う（AI分析・スキルの自動更新では、メンバーの名前・タスクの内容・進捗の記載をこの接続先に送る） | 空 |
| `AI_API_KEY` | APIキー（接続先が求める場合。あるときだけ `Authorization` ヘッダに付ける） | 空 |
| `AI_MODEL` | 使用するモデル名（接続先で利用できるもの）。`AI_API_URL` と `AI_MODEL` の両方が設定されるまでAIは使わない（週報はルールベースで作成、スキルの説明の「AIで下書き」・スキルの自動更新・スキルマップのAIは使えず、AI分析はアプリの集計とルールの推奨アクションだけ） | 空 |
| `AI_TIMEOUT` | AIの応答待ちタイムアウト（秒。1以上の整数でなければAIを使わない） | `60` |
| `MAIL_SMTP_SERVER` | メール送信サーバー（ホスト名またはIPアドレス）。空ならメール送信不可。暗号化・認証なしで送信するため、認証なしで送信できるサーバーを指定 | 空 |
| `MAIL_SMTP_PORT` | 送信サーバーのポート番号（1〜65535 の整数。未設定・範囲外・数字でない値のときは、送信サーバーに接続せず、メール接続テスト・週報・期限超過通知・定型業務リマインドの画面に「ポート番号（MAIL_SMTP_PORT）が未設定です／正しくありません」と表示します） | `25` |
| `MAIL_FROM` | 差出人アドレス。テスト送信・メール接続テストはこのアドレス宛てに送る | 空 |
| `MAIL_TO` / `MAIL_CC` | 宛先（To）・同報（Cc）のアドレス一覧（週報・期限超過通知の両方に使う）。宛先は環境ごとに、各環境のシステム設定の「メールの宛先」タブで設定します（基本設定の画面には出しません）。ここの値は、メインの環境で「メールの宛先」をまだ保存していないあいだの宛先です | `[]` |
| `MAIL_ALLOWED_DOMAINS` | **送信を許可するドメイン**の一覧（例: `["example.com"]`。サブドメインも含む）。設定すると、差出人・宛先・同報・メンバーのメールアドレス・定型業務リマインドの追加の宛先は、このドメインのアドレスだけを保存でき、ほかのドメインのアドレスには送信しない。未設定（空）なら制限しない | （記載なし＝制限なし） |
| `APP_BASE_URL` | メールに載せるタスク・定型業務へのリンクの基準URL（メンバーの PC からこのアプリを開くときの URL。末尾の `/` は不要）。空ならリンクなし（タスク名・業務名だけ）。期限超過通知と定型業務リマインドのメールに使う | 空 |

**送信を許可するドメイン（`MAIL_ALLOWED_DOMAINS`）** は、システム管理の「基本設定」の「宛先」で設定します（1行に1件。「@」の後ろの部分。`*` は不要で、`example.com` と書くと `mail.example.com` などのサブドメインも含みます）。同梱の `config.py` にはこの項目を書いていません（`config.py` は変えていないため。書かれていなければ未設定＝制限なしです）。初期値にしたいときは、サーバーの上の `config.py` に `MAIL_ALLOWED_DOMAINS = ["example.com"]` のように書き足します。
- 保存のとき: 差出人・宛先（To）・同報（Cc）の保存、ドメインの保存（今の差出人・宛先・同報がそのドメインでなければ保存しない。一緒に直して保存）、メンバーのメールアドレスの登録（ユーザーメニュー・チーム管理）、リマインドの追加の宛先（アドレス）の保存で、ドメイン以外のアドレスを断ります。
- 送信のとき: ドメイン以外の宛先（To・Cc）には送らず、結果に「送信を許可するドメイン以外の宛先には送っていません」と出します（To が1件も残らないときは送りません。テスト送信は差出人がドメイン以外なら送りません）。設定する前に登録したドメイン以外のアドレスにも送りません（基本設定・チーム管理・業務の詳細に注意を表示します）。「制限しない」にチェックして保存すると、画面の設定を空（制限なし）にします。

サーバーの上で `config.py` に直接書く場合の記入例（値はすべて例です。コミットしないこと）:
```python
AI_API_URL = "https://ai.example.com/v1/chat/completions"   # ChatGPT互換（OpenAI互換の形式）のAPI
AI_MODEL = "my-model"
MAIL_SMTP_SERVER = "smtp.example.com"
MAIL_FROM = "noreply@example.com"
MAIL_TO = ["manager@example.com"]
APP_BASE_URL = "http://192.0.2.10:8050"    # メールのリンク用（サーバーのアドレスと起動時の --port）
```

`instance/settings.json` の形式（アプリが書きます。手で編集する必要はありません）:
```json
{"values": {"MAIL_SMTP_SERVER": "smtp.example.com", "ADMIN_PASSWORD": "..."}, "updated_at": "2026-10-10 09:00", "updated_by": "kacho", "version": 3}
```
`values` にある項目が有効な値（空でも）、無い項目は `config.py` の値です。`version` は保存のたびに1増え、画面を開いた後にほかの保存があったかの確認に使います。`updated_by` は保存した人のログインID（`SECRET_KEY` の自動生成は「自動生成」、`import-old-config` は「移行」）です。

メールの送信方法: `smtplib.SMTP(MAIL_SMTP_SERVER, MAIL_SMTP_PORT, timeout=20)` で接続し、`sendmail(MAIL_FROM, MAIL_TO＋MAIL_CC, メッセージ)` で送ります（**暗号化〔STARTTLS〕・認証〔ログイン〕は行いません**）。メッセージには `Date`・`Message-ID` を付け、HTML版がある場合は `multipart/alternative`（テキスト版＋HTML版）、週報は Word ファイルを添付します。テスト送信は差出人（`MAIL_FROM`）だけに送ります（Cc なし）。`sendmail` に渡す宛先は表示名を外したアドレスで、To と Cc に同じアドレスがある場合（「表示名 <アドレス>」とアドレスだけの書き方、大文字・小文字の違いを含む）は1通だけ届けます（ヘッダの To / Cc は設定どおり）。

## システム設定

マネージャーがナビの「**システム設定**」（`/system/settings`）から、その環境の設定を1つの画面で変更します（メンバーには表示されず、URL を直接開いても 403。未ログインならログイン画面）。すべての環境で共通の基本設定（接続先・パスワードなど）・環境・勤務パターンは、admin の「[システム管理](#システム管理admin)」で変更します。

### タブ
タブごとにフォームと保存ボタンが分かれていて、保存したタブの内容だけが保存されます。開いているタブは URL（`?tab=recipients` / `weekly` / `overdue` / `skill_ai` / `analysis` / `reminder`。`#weekly` のような指定も可）に残るので、再読み込み・保存後も同じタブが開きます。

| タブ | 内容 | 保存先 |
|------|------|------|
| メールの宛先 | この環境の週報・期限超過通知の宛先（To）・同報（Cc）。すべての環境で共通の設定（送信サーバー・差出人・送信を許可するドメインなど）は読み取り専用で表示 | `env_mail_settings.json`（メインの環境は `instance/`、ほかの環境は `instance/envs/<キー>/`） |
| 週報 | 自動送信する/しない・曜日・時刻・対象期間のルール・対象者・文章の見本と注意点・ファイル名/件名のパターン・メール本文 | `instance/weekly_settings.json` |
| 期限超過通知 | 自動送信する/しない・送信時刻・表示するコメント件数 | `instance/overdue_settings.json` |
| スキル（AI） | タスクの完了からのスキルの自動更新をする/しない（既定はする）・1回の完了で上げる段階の上限（1〜3。既定 1）・最近の判定 | `instance/skill_ai_settings.json` |
| AI分析 | 期限が近いとみなす営業日数（N1）・記載がないとみなす営業日数（N2）・1回に送る材料の最大文字数 | `instance/ai_analysis_settings.json` |
| 定型業務リマインド | 自動送信する/しない・送信時刻1・2・営業日だけ送る。状況（次回の送信・前回の結果・送れない宛先）・宛先ごとのメールのプレビュー・テスト送信 | `instance/routine_reminder_settings.json` |

「メールの宛先」タブは、どの環境も同じです（ほかの環境は、メインの環境の宛先・`config.py` の宛先には送りません）。メインの環境で「メールの宛先」を保存するまでは、以前の基本設定の宛先（画面の設定・`config.py` の `MAIL_TO`・`MAIL_CC`）を表示し、その宛先に送ります。画面に出した今の宛先のままの欄は確かめ直しません（基本設定と同じ。以前の基本設定から引き継いだ、表示名に「,」を含む宛先などがあっても、もう一方の欄を保存できます）。以前の「基本設定」「環境」のタブ（`?tab=config`・`?tab=envs`）は、admin が開くとシステム管理の画面へ移動し、マネージャーには「メールの宛先」タブを表示します（以前の基本設定の保存・接続テストの URL もシステム管理へ転送します。admin だけが使えます）。

週報・期限超過通知・スキル（AI）・AI分析・定型業務リマインドのタブも、画面を開いた後にほかの操作（別のタブ・別のマネージャー）で変わった設定を、古い画面の保存で上書きしません（保存せずに案内を表示し、変わった項目を今の設定に、ほかの項目を入力中の値にした画面を出します。その画面からもう一度保存できます）。

各機能の画面には、実行と状況の表示だけが残ります（設定へは各画面の「設定はシステム設定で変更」のリンクから移動できます）。

| 機能の画面 | 残っているもの |
|------|------|
| 週報（`/weekly/`） | 次回の自動送信・前回の結果・メール/AI の設定状況・今すぐ作成（ダウンロード/テスト送信/本番送信）・現在の設定の概要（ファイル名/件名のプレビュー） |
| 期限超過通知（`/overdue/`） | 次回の自動送信・前回の結果・メール/リンクの設定状況・今すぐ送信（テスト/本番）・現在の設定の概要・メールのプレビュー |

以前の設定の URL（`POST /weekly/settings`・`POST /overdue/settings`）は、システム設定の該当タブ（またはその保存）へ転送されます。

## システム管理（admin）

固定ローカル管理者（`admin`）だけの画面です（`/admin/`）。admin はこのアプリ全体の管理者で、ログインの後はこの画面を表示します（ログインの前に開こうとしていた画面があればその画面）。ほかの人が開くと 403（「システム管理（…）は、固定ローカル管理者（admin）だけが使えます」）、未ログインならログイン画面です。画面の上のナビは、システム管理の項目（トップ・環境・基本設定・勤務パターン）だけです。

| 画面 | 内容 |
|------|------|
| トップ（`/admin/`） | すべての環境（グループ）の一覧（メンバーの人数・停止中）と「開く」、基本設定・勤務パターンへの入口 |
| 環境（`/admin/envs`） | 環境の追加（名前だけ）・名前の変更・停止/再開・開く（「[複数の環境](#複数の環境グループ)」） |
| 基本設定（`/admin/settings`） | すべての環境で共通の設定（「[設定](#設定初期値-configpy-と画面の設定-instancesettingsjson)」の表の項目。宛先の `MAIL_TO`・`MAIL_CC` は環境ごとのため除く）。メール・AI の接続テスト |
| 勤務パターン（`/admin/shifts`・`/admin/shifts/month`） | 勤務の設定と勤務表の入力（Excel で年間分などまとめて取り込み・ひな形のダウンロードもできる。会社の中で共通。すべての環境の出勤表で使う。「[出勤表と勤務](#出勤表と勤務シフト)」） |

- admin は各環境の **担当者・対象者の選択肢と人の一覧に出しません**（タスク・定型業務の担当者、一覧・ガントの担当者の絞り込み、週報の対象者、定型業務リマインドの追加の宛先、チーム管理、出勤表、マネージャーダッシュボードの負荷・活動状況）。以前から admin が担当になっているタスク・定型業務は、担当のまま残し（編集の画面でも選んだまま）、業務が残っていれば絞り込み・負荷にも出します（年休がある月は出勤表にも出します）。
- 「開く」で、その環境にその環境のマネージャーと同じ権限で入ります（初めて入るときに、その環境に admin のユーザーを用意します）。環境の中では、ナビの「**システム管理**」でこの画面に戻れます。環境が1つのあいだも同じです（「開く」はメインの環境のマネージャーダッシュボード）。
- 各環境のマネージャーは、今までどおりその環境の中（タスク・定型業務・スキル・チーム・出勤表の年休・定期メールの設定・メールの宛先など）を編集します。基本設定・環境・勤務パターンは変えられません（出勤表の「勤務表の入力」「勤務の設定」のボタンは admin にだけ表示します。メンバーの勤務は各環境のチーム管理で選びます）。
- 以前の URL（勤務の設定・勤務表の入力の `/leaves/shifts…`、基本設定の保存・接続テストの `/system/settings/config` など、環境の追加・名前の変更・停止の `/system/settings/envs…`）は、システム管理の画面へ移動・転送します（admin だけが使えます）。

### 基本設定
- 項目は「ログイン・セキュリティ / LDAP / AI / メール送信 / 宛先 / リンク」に分けて表示します。項目の定義（表示名・説明・種類・再起動の要否・秘密かどうか）は `app.py` の `FIELDS`（「11-1」）の1か所にあります。項目ごとに **初期値（`config.py`）・画面の設定（`instance/settings.json`）・有効な値** と、どちらの層が有効か（「有効」の印）を表示します。入力欄には画面の設定を表示し（空欄は「画面の設定なし」。初期値を薄く表示）、**空欄のまま保存するとその項目は変更しません**。画面の設定がある項目には「**初期値に戻す**」のチェックがあり、保存すると `settings.json` からその項目を外して `config.py` の値に戻します（チェックすると入力欄を空にして入力できなくします。入力欄に表示していた今の値のまま送られた場合も「初期値に戻す」として受け付け、別の値の入力と同時には指定できません）。
- 定義の無い項目（`config.py` にだけ書かれている項目、`config.py` で上書きした固定設定〔`APP_NAME` / `SESSION_COOKIE_SAMESITE` など〕）は「**その他**」に読み取り専用で表示されます（画面から変更できない項目が黙って抜け落ちないように）。以前の版の項目（`SERVER_HOST` / `SERVER_PORT` / `MAIL_USE_TLS` / `MAIL_USERNAME` / `MAIL_PASSWORD` / `MAIL_TEST_TO` / `OVERDUE_MAIL_TO` / `OVERDUE_MAIL_CC`）が `config.py` に残っている場合は、ここに「**未使用**」と使わない理由を表示します（アプリは `config.py` を書き換えないため、不要なら直接消してください）。
- **画面の設定のファイルが読めないとき**: `instance/settings.json` が壊れている（JSON として読めない・形式が違う）場合は、画面上部にその旨を表示し、基本設定は **保存できません**（初期値と実行中の値を表示します。上書きはしません）。ファイルを直すか、名前を変えて（画面の設定を捨てて）ください。
- 入力の確認: URL は `http://` / `https://`（ID・パスワードを含む `https://user:pass@host/` の形は不可。`APP_BASE_URL` は「?」「#」を含めない〔`…/?`・`…/#` のように末尾だけでも不可〕）、送信サーバーはホスト名・IPv4 アドレス・IPv6 アドレス（`[ ]` なし）だけ（`smtp.example.com:587` のようにポート番号を付けた値は不可。ポート番号は「ポート番号」の欄）、送信サーバーと URL のホスト名は「.」で始まる名前（`.smtp.example.com`）・「.」が続く名前・「.」で区切った1つの部分が64文字以上の名前・全体が253文字を超える名前は不可（接続のときに必ず失敗するため。`config.py` の直接の編集などでこのような値になっているときは、接続テスト・送信の結果に「送信サーバー（…）の名前の形式が正しくない」「AI_API_URL の接続先のホスト名の形式が正しくない」と表示します）、ポートは 1〜65535、`AI_TIMEOUT` は 5〜600 秒、`AI_API_URL` と `AI_API_KEY` は半角英数字・記号だけ（AI の呼び出しは URL・キーに全角の文字・日本語を含められないため。日本語のドメイン・パスはピュニコード・パーセントエンコードにしたもの）、アドレスの一覧は1行に1件（「,」「;」区切りも可。`name@example.com` の形式を確認）、改行・制御文字は不可。アドレスの表示名（`表示名 <name@example.com>`）に「"」「,」「;」「<」「>」は使えません（「,」「;」は区切りとして扱うため）。誤りが1つでもあれば **何も保存せず**、入力中の内容（パスワード・キーを除く）を残してメッセージを表示します。画面に表示した今の値のままの欄（変更していない欄）は確認し直さず、今の値のまま残します（`import-old-config` で取り込んだ `'"表示名" <アドレス>'`・表示名に「,」を含む宛先・`AI_TIMEOUT = 60.0` など、アプリでは使えるが入力欄の確認より広い書き方の値があっても、ほかの項目を保存できます）。
- **保存の仕組み**: 変わった項目だけを `instance/settings.json` の `values` に書き（「初期値に戻す」はその項目を外す）、`updated_at`・`updated_by`・`version` を更新して、一時ファイル経由で置き換えます（書き込みの途中で壊れたファイルを残しません）。`config.py` は書き換えません。画面を開いた後にほかの保存（ほかの人・別のタブ）で `version` が変わっていた場合は保存せず、最新の内容を表示します（同じ画面からの二度押しは「既に保存されています」）。
- **ID・パスワードを含む URL**: `import-old-config` などで `AI_API_URL` / `LDAP_API_URL` / `APP_BASE_URL` に `https://user:pass@host/` の形の値が入っているときは、入力欄では `https://***@host/` と伏せて表示し、直す案内を出します（その値のままでは保存できません。AI にも送りません）。「その他」の項目は、名前に `KEY` / `PASS` / `PW`（`PWD`・`LDAP_BINDPW`・`LDAP_ROOTPW` なども）/ `SECRET` / `TOKEN` / `CRED`（`CREDENTIAL`・`LDAP_CREDS` なども）/ `AUTH` / `PRIVATE` を含むものの値を表示しません。値が辞書（一覧の中・入れ子も）で、そのキーの名前が同じく秘密の値らしいもの（`bind_password`・`Authorization` など）を含む項目も、値を表示しません。ほかの項目でも、値の中の URL の ID・パスワード（`user:pass@`。一覧・辞書の中の URL も）は `***@` と伏せて表示します。
- **すぐに反映される項目**: `SECRET_KEY` 以外は、保存と同時に実行中のアプリにも反映されます（メール・AI・リンク・admin のパスワードなど）。同じフォルダで2つ以上のサーバーを起動しているとき（`--debug` の自動送信を行う親のプロセスを含む）も、ほかのサーバーは次の画面の表示の前と自動送信の前に、画面から保存された値を反映します（自動送信を行うサーバーが古い宛先・送信サーバー・リンクで送らないように）。`LDAP_API_URL` をどう使うかは `ldap_client.py` の実装によります。
- **再起動が必要な項目**: `SECRET_KEY` はファイルにだけ保存され、サーバーの再起動後に反映されます。保存した値と実行中の値が違うあいだ、画面上部に「**再起動が必要な変更があります**」と項目名を表示します。
- **秘密の値**（`SECRET_KEY` / `ADMIN_PASSWORD` / `AI_API_KEY`）: 画面には「設定あり／未設定」だけを表示し、値は HTML・ログ・メッセージのどこにも出しません。入力欄を **空欄のまま保存すると変更しません**。ただし接続先（`AI_API_URL` のホスト・ポート・http/https）を変えるときは、保存済みのキーを新しい接続先へ送らないよう、`AI_API_KEY` を入力し直す（今と同じキーを入力し直してもかまいません）か「空にする」を指定します。`AI_API_KEY` を「初期値に戻す」で `config.py` のキーにするときは、接続先も `config.py` の接続先でなければ保存できません（`config.py` のキーは `config.py` の接続先にだけ使います。画面の設定で別の接続先にしたまま `config.py` のキーを使うことはできず、その接続先に使うキーは入力し直します）。空にするときは「**空にする**」にチェックします（画面の設定を空にし、`config.py` の値も使いません。`ADMIN_PASSWORD` を空にすると admin のログイン可否は `ldap_client.py` の判定に任されます）。`ADMIN_PASSWORD` の変更は確認のため2回入力します（8文字以上）。`SECRET_KEY` は自由に入力できず、「**新しいキーを生成**」でランダムな値（`secrets.token_hex(32)`）を作ります。新しいキーは再起動後に有効になり、そのとき **全員がログアウト** されます。
- **接続テスト**: 「メール接続テスト」は差出人（`MAIL_FROM`）宛てに短いテキストのメールを1通送り（送信サーバーに断られたときは、接続の直後・あいさつ〔EHLO/HELO〕・差出人・宛先・本文の送信のどの段階でも、サーバーの応答〔コードと本文。例: `530 5.7.57 …`〕と、分かる場合は原因〔ログイン・暗号化が必要なサーバー、このPCからの中継が許可されていない、メールが大きすぎるなど。応答の中のアドレスの文字では判断しません〕を表示します。接続の直後に切断されたときは、サーバー名・ポート番号と接続の許可の確認を案内します。接続できても応答が無いときは、ポート番号の確認を案内します〔465 などの暗号化した接続には対応していません〕。本文を受け付けた後の切断のあいさつ〔QUIT〕に送信サーバーが 221 以外を返しても、送信済みとして扱います。週報・期限超過通知の送信の結果も同じ）、「AI接続テスト」は AI に短い問い合わせを1回送ります（AI が未設定〔接続先・モデル名・タイムアウトのどれかが無い〕のあいだはボタンを押せず、送りません）。どちらも **保存済みの設定（有効な値）** を使い、結果（OK またはエラー。パスワード・キーは伏せ字。AI の応答は伏せ字にしてから80文字までに短くする。AI の応答に表示できない文字〔絵文字の途中で切れた文字など〕があれば除く）を画面に表示します。
- `config.py` はサーバーの上で **直接編集してもかまいません**（直接編集した値はサーバーの再起動で反映。画面の設定がある項目は画面の設定が優先）。

## 週報（自動作成・メール送信）

マネージャーがナビの「**定期メール**」→「**週報**」から、今すぐ作成・前回の結果の確認を行います。曜日・時刻・対象者・見本などの設定は「**システム設定**」の「**週報**」タブで変更します（メンバーには表示されません）。

### 作成される週報
- 1回の作成で **Word ファイル1つ**。構成は「タイトル・対象期間」→「**チーム全体**」のまとめ（文章＋メンバー別の集計表）→ 改ページして **1人1ページ** の個人分。
- 材料は **タスク情報だけ** です（担当タスク・進捗状況の記載・ステータス変更・成果・規模/負荷）。定型業務の内容・年休・スキルは載せません（負荷の数値＝月間負荷h・余力h のみ使用）。
- 件数・成果（年換算）・メンバー別の数値は **プログラムで集計** します（複数担当のタスクはチーム全体では1件として数えます）。AI には数値を計算させません。
- **期限超過** は、未完了で期限が「期間の最終日の翌日」と「作成した日」の早いほうより前のタスクです。「送信日を含む7日間」のように期間が作成日（送信日）を含むときも、今日が期限のタスクは期限超過にせず「期限が近い」に入れます（期限超過通知・ダッシュボードと同じく、期限が今日より前のものだけが期限超過）。
- 期間内に動きの無い人も載せ、「今週の記載なし」と未完了の担当タスクを表示します（この人の分は AI を使いません）。
- タスクの開始日・期限は `mm/dd`（期間の最終日と違う年は `yyyy/mm/dd`。前の年からの期限超過が数日の遅れに見えないように）で書きます（Word・AI に渡す材料とも）。記載・完了・状態の変更の日付は期間の中のため `mm/dd` です。
- AI（システム管理の「基本設定」の `AI_〜`。接続先とモデル名の両方）が設定されていれば、各人の分（1人1回）とチーム全体（1回）を AI が見本どおりに整えます。AI が未設定・失敗した部分はルールベースの文章になり、文書に「AI未整形」と注記されます（AI は部分ごとに呼び出すため、一部が失敗しても他の部分は AI で整形されます）。

### 自動送信
- 設定した **曜日・時刻に1回だけ** 作成し、本番の宛先（`MAIL_TO` / `MAIL_CC`）へそのまま送信します（承認の手順はありません）。実行した日付・時刻の印を `instance/weekly_settings.json`（`last_auto_key`）に残すため、その時刻の1分の間にサーバーを再起動しても2回は送りません。印の日付で比べるため、その日に送った後に時刻を後の時刻に変えても、その日はもう一度送りません（「次回の自動送信」も次の週の日時になります）。
- 動くのは `flask --app app run` で起動したサーバーが動いている間だけです。サーバーが止まっている間に過ぎた分は、後から送信しません。
- 実行履歴は残さず、**前回の結果**（日時・きっかけ〔自動/手動/テスト〕・成否・メッセージ）だけを画面に表示します（毎回上書き）。

### 設定項目（システム設定の「週報」タブ）
| 項目 | 内容 |
|------|------|
| 自動送信する | オン/オフ（既定はオフ） |
| 曜日・時刻 | 自動送信する曜日と時刻（既定: 月曜 08:00） |
| 対象期間のルール | 「送信日の前日までの7日間」（既定）／「送信日を含む7日間」。「送信日を含む7日間」では、送信日の送信時刻より後に記録した内容はどの自動送信の週報にも載りません（次回の期間は翌日から始まるため）。漏れなく載せたい場合は既定のルールを使ってください |
| 対象者 | 週報に載せる人（有効なユーザーから選択。全員選択/全解除あり）。チーム全体のまとめも選んだ人の担当タスクが対象。新しく登録したユーザーは自動では選ばれません。無効化したユーザーは選んでいても載りません（無効のあいだはここに表示されませんが、このタブを保存しても選択は残り、復帰すると対象に戻ります） |
| チーム全体の見本／個人の見本／書く際の注意点 | AI が見出し・順序・口調・分量を合わせる見本（見本に書いた事実は使いません）。見出しは「■」、箇条書きは「・」で始めます。差し込み記号 `{期間}` `{氏名}` `{作成日}` が使えます |
| ファイル名・メール件名のパターン | 既定は `週報_{開始日}-{終了日}.docx` と `【週報】{期間}`。今日作成した場合のプレビューを表示（週報の画面にも表示）。パターンはファイル名 200文字・件名 300文字まで（見本・注意点・メール本文は 20000文字まで。超えたときは保存せずに表示） |
| メール本文 | 送信するメールの本文 |

ファイル名・件名・メール本文で使える差し込み記号:

| 記号 | 内容 |
|------|------|
| `{開始日}` `{終了日}` `{送信日}` | 日付（`yyyymmdd`） |
| `{年}` `{月}` | 対象期間の終了日の西暦年（4桁）・月（2桁） |
| `{週}` | 対象期間の終了日の ISO 週番号（2桁） |
| `{週の年}` | `{週}` の属する年（ISO 週の年・4桁）。年末年始は `{年}` と異なることがあるため、週番号と組み合わせるときはこちらを使います（例: `週報_{週の年}W{週}.docx`） |
| `{期間}` | `yyyy/mm/dd〜yyyy/mm/dd`（ファイル名では `/` を `-` に置き換え） |

ファイル名に使えない文字（`\ / : * ? " < > |` と制御文字）は `_` に置き換え、拡張子 `.docx` を付け、長さは120文字までに切り詰めます。

### 今すぐ作成（週報の画面）
期間（開始・終了）を指定して、**Wordをダウンロード**／**テスト送信**（差出人〔`MAIL_FROM`〕宛て。Cc なし）／**本番の宛先に送信**（確認あり）ができます。送信はバックグラウンドで行い、結果は「前回の結果」に表示されます。期間は366日以内で、終わりの日は 9999/12/23 まで（それより後は入力の誤りとして断ります）。開始・終了に日付として読めない値（`2026/03/01`・`2026-02-30` など）が送られたときは、既定の期間に置き換えず「期間の日付が正しくありません」と表示して、作成・送信しません（欄が空のときだけ「対象期間のルール」の既定の期間を使います）。
各人の月間負荷・余力は、マネージャーダッシュボードの「ヒト別 負荷・案件状況」と同じ計算です（複数担当のタスクは有効な担当者の数で均等割り。対象に選んだ人によって値は変わりません）。
Word ファイルのプロパティの作成者・最終更新者はアプリの名前（`APP_NAME`）、作成日時・更新日時は作成した日時です。

### 保存場所（DB には保存しません）
- 画面の設定と前回の結果: `instance/weekly_settings.json`（Git 管理外。画面で保存したとき・送信したときに作成。無ければ既定値）。ファイルが壊れていて読み込めない場合は既定値（自動送信オフ）で動き、保存済みの内容を消さないよう上書きもしません。週報の画面とシステム設定の「週報」タブにその旨を表示し、今すぐ作成・送信もできなくなります（ファイルを修正するか削除してください）
- メールの送信サーバー・AI の接続先とキー: 基本設定（初期値 `config.py` ＋ 画面の設定 `instance/settings.json`。システム管理の「基本設定」〔admin〕で変更。週報の画面では「設定あり/未設定」などを読み取り専用で表示）。宛先: その環境のシステム設定の「メールの宛先」タブ（`env_mail_settings.json`）

## 期限超過通知（毎朝のメール）

マネージャーがナビの「**定期メール**」→「**期限超過通知**」から、プレビュー・今すぐ送信・前回の結果の確認を行います。自動送信・時刻・コメント件数の設定は「**システム設定**」の「**期限超過通知**」タブで変更します（メンバーには表示されません）。
営業日の毎朝、期限を過ぎた未完了タスクの一覧を **1通のメール** で送ります（DB には何も保存しません）。

### メールの内容
- **期限超過** = 期限が今日より前で、完了していないタスク。状態で「未着手／進行中」と「保留」の2つの区分に分けます（完了したタスクは載せません）。
- 各区分の中は **担当者ごと** にまとめます。複数担当のタスクは各担当者の下に載せ、担当者がいないタスクは「担当者なし」にまとめます。無効化したユーザーが担当のタスクもその人の下に載せ、名前に「［無効］」を付けます（担当の付け替えが必要なことが分かるように）。
- 担当者は **件数の多い順**（同数なら表示名順）、タスクは **期限の古い順** に並べ、タスク名の横に期限（例: `期限 10/01`。今年以外は年も表示）を付けます。未着手／進行中の区分では状態も表示します。
- 各タスクに **直近の進捗記載（コメント）** を「表示するコメント件数」まで古い順に載せます。経過日数は土日祝を除いた営業日で数え（例: `3日前（土日祝除く）`、今日の記載は `本日`。土日祝に送ったとき〔手動の送信・テスト送信・プレビュー〕は、直前の営業日とその後の土日祝の記載を `1日前（土日祝除く）` として数え、1通の中では古い記載ほど日数が大きくなります）、記載日と記載者を添えます。コメントはタスク名の次の行から1件ずつ書き、本文は1行にまとめ（改行は空白に）、長いものは約200文字で切ります。記載が無いタスクは「コメントなし」。
- 期限超過が0件の日も送信し、空の区分には「該当なし」と書きます。
- タスク名には **タスク詳細画面へのリンク**（`APP_BASE_URL` ＋ `/tasks/<ID>?t=<印>`。印はタスクごとの12文字）を付けます。印があるため、そのタスクが削除されて番号が新しい別のタスクに使われた後にリンクを開くと、新しいタスクではなく 404（見つかりません）になります。`APP_BASE_URL` が空（または形式が不正）ならリンクは付けず、期限超過通知の画面に警告を表示します（前回の結果にも「リンクなし」と残ります）。
- テキスト版とHTML版の両方を入れて送ります（`multipart/alternative`）。テキスト版はタスク名の後ろに括弧でURL、HTML版はタスク名がリンクになります（Outlook などでも読めるよう簡単な書式だけを使用）。
- 件名の例: `【期限超過】2026/10/05 未着手・進行中 3件／保留 1件`（件数はタスクの数。複数担当でも1件）

本文の形:
```
■未着手／進行中　期限超過一覧
Aさん（5件）
　タスク名（リンク）［進行中・期限 10/01］
　　【3日前（土日祝除く） 09/30 A】直近の進捗記載
...
■保留　期限超過一覧
Bさん（2件）
　タスク名（リンク）［期限 09/20］
　　コメントなし
```

### 自動送信
- **営業日**（月〜金で、日本の祝日・振替休日・国民の休日でない日）の設定時刻に1回だけ送ります（既定 05:00。実行した日付・時刻の印を `instance/overdue_settings.json` の `last_auto_key` に残すため、その1分の間にサーバーを再起動しても2回は送りません。印の日付で比べるため、その日に送った後に時刻を後の時刻に変えても、その日はもう一度送りません〔「次回の自動送信」も次の営業日になります〕）。土日・祝日は送りません。祝日はライブラリを使わずに法律のルールから計算します（`app.py` の「2-4. 営業日カレンダー」。春分・秋分は1980〜2099年の計算式）。独自の休業日（年末年始の休みなど）は考慮しません。
- 動くのは `flask --app app run` で起動したサーバーが動いている間だけです。サーバーが止まっている間に過ぎた分は、後から送信しません。
- 宛先は週報と同じ `MAIL_TO` / `MAIL_CC` です。
- 実行履歴は残さず、**前回の結果**（日時・きっかけ〔自動/手動/テスト〕・成否・メッセージ）だけを画面に表示します（毎回上書き）。

### 設定項目（システム設定の「期限超過通知」タブ）
| 項目 | 内容 |
|------|------|
| 自動送信する | オン/オフ（既定はオフ） |
| 送信時刻 | 自動送信の時刻（既定 05:00）。営業日だけ送信 |
| 表示するコメント件数 | 各タスクに載せる直近の進捗記載の件数（1〜10、既定 1） |

### 画面（期限超過通知の画面）
| 項目 | 内容 |
|------|------|
| 状況の表示 | 次回の自動送信日時（次の営業日。今日の時刻を過ぎていれば翌営業日）、前回の結果、メールの設定状況（使われる宛先を含む）、`APP_BASE_URL` の設定状況 |
| プレビュー | 今この時点のメールの内容（件名・HTML版・テキスト版） |
| テスト送信 | 差出人（`MAIL_FROM`）宛てに今の内容を送信（Cc なし） |
| 今すぐ本番の宛先に送信 | 本番の宛先に今の内容を送信（確認あり） |

送信はバックグラウンドで行い、画面はすぐに戻ります（結果は「前回の結果」に表示）。

### 保存場所（DB には保存しません）
- 画面の設定と前回の結果: `instance/overdue_settings.json`（Git 管理外。画面で保存したとき・送信したときに作成。無ければ既定値）。読み込めない場合の扱いは週報と同じです（既定値〔自動送信オフ〕で動き、上書きしません。期限超過通知の画面とシステム設定の「期限超過通知」タブにその旨を表示し、今すぐ送信もできなくなります）
- メールの送信サーバー・リンクの基準URL: 基本設定（初期値 `config.py` ＋ 画面の設定 `instance/settings.json`。システム管理の「基本設定」〔admin〕で変更。期限超過通知の画面では読み取り専用で表示）。宛先: 週報と同じく、その環境のシステム設定の「メールの宛先」タブ

## 定型・定期業務のリマインド（メール）

定型・定期業務の **実施日** に担当者へメールで知らせ、その回の **完了の入力** があるまで、1日2回（送信時刻1・2。既定 09:00・15:00）リマインドのメールを送ります。
業務ごとの実施日・追加の宛先は、定型業務の登録・編集の画面の「**リマインド**」の欄で設定します（権限は業務の登録・編集と同じ。メンバーは自分が担当者の1人の業務、マネージャーはすべて。ただし追加の宛先の **アドレス** を設定・変更できるのはマネージャーだけです）。
自動送信のオン/オフ・時刻は、マネージャーが「**システム設定**」の「**定型業務リマインド**」タブ（ナビの「定期メール」→「定型業務リマインド」からも開けます）で変更します。

### 実施日（業務ごとの「リマインド」の欄）
| 項目 | 内容 |
|------|------|
| リマインドする | オン/オフ（オフのあいだは、未完了の回の表示とメールの送信をしません） |
| 繰り返し | **毎営業日**（土日・祝日を除く毎日）／**毎週**（曜日。複数可）／**毎月**（1〜31日・月末・最終営業日。複数可。その月に無い日〔2月30日など〕は月末）／**指定日**（日付を1行に1つ） |
| 営業日でない日に当たったとき | **前の営業日にする**（既定）／次の営業日にする／その日のまま（毎営業日・最終営業日では使いません）。ずらした結果、同じ日になったものは1回にします |
| 開始日 | この日より前の実施予定日は作りません（既定は今日）。開始日から今日までの回をまとめて作るため、今日から31日より前の日にはできません（保存済みの開始日のまま、ほかの項目を変えるのはかまいません） |
| 追加の宛先 | メンバー（複数可）と、アドレス（1行に1件・1業務に10件まで。**設定・変更できるのはマネージャーだけ**）。担当者には自動で送ります |

- **追加の宛先（アドレス）はマネージャーだけ**: メンバーの画面ではアドレスの欄は読み取り専用で、メンバーが保存してもアドレスは今のまま変わりません（メンバーは追加の宛先〔メンバー〕を選べます。アドレスはその人のメールアドレス）。ログインできる人なら誰でも、会社の差出人で任意の社外のアドレスへ繰り返し送れてしまわないためです。送るのは、今のアドレスをマネージャーが保存したものだけです（DB の新しいテーブル `routine_reminder_email_checks` に、マネージャーが保存したアドレス・保存した人・日時を記録します）。
  - 以前の版でメンバーが入力したアドレス（最後に保存した人がメンバーの業務）は、データはそのまま残しますが、**マネージャーがその業務の「編集」で保存するまで送りません**。業務の詳細の「リマインド」とシステム設定の「定型業務リマインド」タブに「追加の宛先: アドレス N件（マネージャーの確認待ち）」と表示し、編集画面にも案内を出します（不要なアドレスは消してから保存してください）。以前の版で最後にマネージャーが保存した業務のアドレスは、今までどおり送ります。
  - 追加の宛先のアドレスのドメインは、システム設定の「送信を許可するドメイン」（`MAIL_ALLOWED_DOMAINS`）を設定したときだけ制限します（そのドメイン以外のアドレスは保存・送信しません。未設定なら制限しないため、社外の関係者に送ることもできます）。
- 業務の詳細の「リマインド」には宛先を表示します。アドレスは業務を編集できる人（担当者・マネージャー）にだけ表示し、メンバーが登録したアドレスは **マネージャーとその本人にだけ** 表示します（メンバーが自分の業務の追加の宛先にほかの人を選んでも、その人のアドレスは見えず「アドレス登録済み」と表示します）。

- 営業日は期限超過通知と同じ（土日と日本の祝日・振替休日・国民の休日。独自の休業日は考えません）。
- 実施予定日の回は、画面を開いたとき・送信のときに「開始日〜今日」の分をまとめて作ります（未来の日は作りません）。同じ業務・同じ日の回は1つだけです。
- **予定の作り方を変えたとき**（繰り返し・曜日・日・指定日・営業日でない日の扱い）と **オフからオンにしたとき** は、今日より前の日の予定を新しいルールで作らないよう、開始日を今日にします（画面に案内を表示します）。同じ保存で開始日も変えたときは、入力した開始日から作ります。**既に作った回（未完了・完了とも）はそのまま残ります**（変えるのはまだ作っていない回だけ）。変える前のルールの今日までの回は、変える前に作っておきます。
- 「リマインド」の欄が無い以前の画面から保存したときは、リマインドの設定を変えません。古い画面からの保存で、ほかの操作で変わったリマインドの項目を上書きしません（業務のほかの項目と同じく「同時に変更された項目」を表示）。
- 業務を削除すると、その業務のリマインドの設定と実施予定日の回も削除します。

### 完了の入力
- 未完了の回（実施予定日が今日以前で、完了の入力が無いもの）には「**完了**」のボタンがあります: 定型・定期業務の一覧の「**未完了の定型業務**」（全員分）、業務の詳細の「リマインド」、個人ダッシュボードの「**今日の定型業務**」（自分が担当の分。メンバーのトップ。マネージャーのトップはマネージャーダッシュボードのため、マネージャーは一覧・詳細・メールのリンクから入力します）。
- 完了を入力できるのは **その業務の担当者（複数担当なら誰でも）とマネージャー** です。完了を入力すると、その回のリマインドはすぐに止まります（送信のたびに未完了の回を読み直します）。同時に押された2回目は「既に完了が入力されています」と表示します。
- 完了の **取り消し** はマネージャーだけです（業務の詳細の「最近の完了」。取り消すと未完了に戻り、リマインドの対象になります）。
- メールの「完了の入力」のリンクは、その回の画面（`/routine/occurrences/<番号>?o=<印>`）を開きます。開くだけでは何も変わらず、画面の「完了」ボタンで入力します。印は回ごとに違うため、業務が削除されて番号が別の回に使われた後にリンクを開いても、別の回は開かずに 404 になります。業務の画面へのリンク（`/routine/<番号>?r=<印>`）も同じです。

### メールの内容
- **宛先ごとに1通** にまとめます。その宛先に関係する業務を「**本日実施予定**」（実施予定日が今日）と「**【リマインド】未完了**」（実施予定日を過ぎたもの。予定日と経過した営業日数〔例: `3営業日経過`〕）に分けて載せ、業務ごとに担当者の名前、業務の画面と完了の入力へのリンク（`APP_BASE_URL` ＋ パス。`APP_BASE_URL` が空・不正ならリンクなし）を付けます。
- 件名の例: `【定型業務】本日実施 2件／未完了 1件`（件数はその宛先に送る回の数）
- テキスト版とHTML版の両方を入れて送ります（期限超過通知と同じ）。To はその宛先だけで Cc はありません。差出人は `MAIL_FROM` です（宛先の `MAIL_TO` / `MAIL_CC` は使いません）。送信の方法は期限超過通知と同じです（暗号化・認証なし）。
- 宛先は、担当者（複数担当なら全員。メールアドレスがあり、有効な人）と、業務ごとの追加の宛先（メンバー〔アドレスがあり、有効な人〕・アドレス〔マネージャーが保存したもの〕）です。同じアドレスには1通だけ送ります。
- **担当者のメールアドレスが未登録のとき**（または無効化されたメンバーのとき）は担当者には送らず、追加の宛先には送ります。業務の詳細とシステム設定の「定型業務リマインド」タブに注意を表示し、前回の結果にも残します。
- 送るもの（未完了の回）が無い宛先には送りません。どの業務にも未完了の回が無ければ、何も送りません。

本文の形:
```
山田 太郎さん

2026/10/07 09:00 時点の、定型・定期業務の本日の実施予定と、完了の入力がまだのもののお知らせです。
実施したら、業務ごとの「完了の入力」から完了を入力してください（入力すると、その回のリマインドは止まります）。

■本日実施予定（1件）
・日次バックアップ確認（担当: 山田 太郎）
　　業務の画面: http://192.0.2.10:8050/routine/1?r=…
　　完了の入力: http://192.0.2.10:8050/routine/occurrences/12?o=…

■【リマインド】未完了（1件）
・月次備品棚卸し［予定日 2026/10/05（月）・2営業日経過］（担当: 山田 太郎）
　　…
```

### 自動送信（システム設定の「定型業務リマインド」タブ）
| 項目 | 内容 |
|------|------|
| 自動送信する | オン/オフ（既定はオフ） |
| 送信時刻1・送信時刻2 | それぞれの時刻に1日1回送ります（既定 09:00・15:00。違う時刻にします）。その日に送った後に時刻を変えても、その時刻の分は翌日から送ります（1日に送るのは2回まで） |
| 営業日だけ送る | オンなら土日・祝日は送りません（既定はオン） |

- その日に送った枠（送信時刻1・2のどちらか）を `instance/routine_reminder_settings.json` の `auto_slots`（例: `{"date": "2026-10-09", "done": ["time1"]}`）に残すため、その1分の間にサーバーを再起動しても2回は送りません。時刻ではなく枠で数えるため、送った後に時刻を後の時刻に変えても、その日はもう一度送りません。動くのは `flask --app app run` で起動したサーバーが動いている間だけで、止まっている間に過ぎた分は後から送りません（週報・期限超過通知と同じスケジューラ）。
- タブには、次回の自動送信・**前回の結果**（日時・きっかけ・成否・送った通数・送れなかった宛先・失敗した宛先と理由）・送れない宛先（アドレス未登録・無効化された担当者と追加の宛先、マネージャーの確認待ちの追加の宛先〔アドレス〕）・**宛先ごとのメールのプレビュー**（今この時点の内容）を表示します。
- **テスト送信**: 今の未完了の回をすべて載せた1通を、差出人（`MAIL_FROM`）宛てに送ります（担当者・追加の宛先には送りません）。

### メールアドレス
- ユーザーのメールアドレスは、各ユーザーがユーザーメニュー（右上の名前）の「**メールアドレス**」（`/account/email`）で登録・変更します。マネージャーは「チーム管理」のメンバーの表で、全員の分を変更できます。
- 形式は `name@example.com` のように半角で、表示名や `< >`・改行は付けません。空にして保存すると削除します。画面を開いた後にほかの操作で変わっていたときは、古い画面の値で上書きしません。
- メンバーを削除（業務データが無く、行ごと削除）するときは、そのメンバーのメールアドレスと、リマインドの追加の宛先からも除きます（番号が次に追加した人に使われても、その人に送らないように）。定型業務の完了を入力した記録のあるメンバーは、削除せずに無効化します。

### 保存場所
- 業務ごとの設定・実施予定日の回・メールアドレス・追加の宛先（アドレス）をマネージャーが保存した記録: DB の新しいテーブル `routine_reminders` / `routine_occurrences` / `user_emails` / `routine_reminder_email_checks`（既存のテーブル〔`users` / `routine_works` など〕は変えません。起動時に自動で作成されます）。
- 自動送信の設定と前回の結果: `instance/routine_reminder_settings.json`（Git 管理外。画面で保存したとき・送信したときに作成。基本設定〔`instance/settings.json`〕には保存しません）。読み込めない場合は既定値（自動送信オフ）で動き、上書きしません（タブにその旨を表示し、テスト送信もできません）。
- 送信サーバー・差出人・リンクの基準URL: 基本設定（初期値 `config.py` ＋ 画面の設定 `instance/settings.json`。システム管理の「基本設定」〔admin〕）。
- Excel 出力: 定型業務（`routine.xlsx`）に「リマインドの設定」「実施予定日と完了」のシート、チーム（`teams.xlsx`）のメンバーのシートにメールアドレスの列があります。

## タスクの登録の支援（必要スキル・推奨の担当者・規模の確認・メールから下書き）

タスクの登録・編集の画面（マネージャー）で使います。

### 必要スキル
- スキル項目ごとに「不要／Lv1〜Lv3」を選びます（複数可）。選んだ到達度は **担当者に必要な到達度の下限** です（到達尺度はスキルマップと同じ）。
- 変えられるのはマネージャーだけです（優先度・日付・担当者と同じ計画の項目。メンバーの編集画面では表示だけ）。タスクの詳細・一覧（表示する項目の「必要スキル」）・Excel 出力（タスクのシートの最後の列）にも出ます。
- 無効にしたスキル項目は選択肢に出ません。必要スキルのまま無効にした項目は「［無効］」を付けて残り、「不要」にすると外れます。画面を開いた後に無効にされた項目を選んで保存したときは、保存せずに選び直しを案内します。ほかの操作で必要スキルが変わっていたときは、ほかの項目と同じく上書きしません。

### 推奨の担当者
登録・編集の画面の「推奨の担当者」に、スキル管理の対象のメンバー（有効なメンバー）を並べます。必要スキル・開始日・期限・規模を変えるたびに表が作り直されます（JavaScript が無効なときは「推奨の担当者を表示」のボタン。入力を残したまま表示し直し、保存はしません）。表の「担当にする」で担当者のチェックを付け外しできます。
- **推奨**: 期間（開始日〜期限）の中に **休み** が無く、出勤日があり、必要スキルの到達度（スキルマップの値。未評価は Lv0）を **すべて満たし**、このタスクを担当した後の負荷が **フルタイム（160h/月）を超えない** メンバー。必要スキルが無ければ休み・出勤日・負荷だけで決めます。
- **休み**: 登録された年休（全休・半休）と、本人の勤務の勤務表で種類が「年休」の記号の日（年休の充当日など）。期間の中に1日でもあれば、その期間は対応できないものとして推奨にしません（表には「休みあり」と休みの日を出します。担当にすることはできます）。時間休（午前時間休・午後時間休）は休みにしません（表には「時間休: 11/05（午前時間休）」のように出します）。
- **期間**: 開始日と期限の間（期限が今日以降なら、今日より前の日は除きます）。期限だけなら今日（期限が過去なら期限の日）〜期限、開始日だけなら開始日の1日（今日より前なら今日）。どちらも無いときは休みを確かめません。期間が長い（800日以上）ときは、出勤日数と勤務表の休みの日は数えず、登録された年休だけを確かめます。
- **出勤日数**: 期間の中の、勤務表で出勤・臨時出勤の日（記号の無い日は土日・祝日以外）。半休の日は 0.5 日、全休の日は数えません（時間休の日は出勤の日として数えます）。
- **負荷（h/月）**: 今の負荷です（担当中の未完了のタスクの規模を、その期間で月あたりにした時間〔複数担当は均等割り〕と、定型業務の月間工数の合計。マネージャーダッシュボードの「ヒト別 負荷・案件状況」と同じ計算。編集中のタスクは含めません）。水準（低・中・高）と、担当中のタスクの数も出します。
- **担当した後・余力**: 今の負荷に、このタスクの規模を期間（開始日〜期限。無ければ規模の目安の日数）で月あたりにした時間（1人で担当したとき）を足した負荷と、フルタイム（160h/月）までの残り（余力）です。超えるときは「負荷超過」と超えた時間を出し、推奨にしません（担当にすることはできます）。規模が未設定のときは、このタスクの時間を足しません（その旨を表示）。
- 並び: 推奨 → 休みが無い（出勤日がある） → 満たす必要スキルの数が多い → 不足の合計が小さい → 負荷超過でない → 担当した後の負荷が小さい → 担当中（未完了）のタスクが少ない → 出勤日数が多い → 必要スキルの到達度の合計が大きい。

### 規模と出勤日数の確認
登録・編集の画面で、**規模（負荷の目安）が、開始日〜期限の出勤日数を超える** ときに、規模の欄の下に案内を出します（例: 「規模（1週＝約40時間）が、開始日〜期限の山田 一郎さんの出勤日数（2日＝16時間。1日8時間で計算）を超えています。期限・規模・担当者を見直してください。」）。
- 出勤日数は、担当者がいればその人たちの出勤日数の合計（勤務表で出勤・臨時出勤の日。記号の無い日は土日・祝日以外。年休の全休の日は除き、半休は 0.5 日、時間休の日は出勤の日。推奨の担当者の出勤日数と同じ数え方）、いなければ営業日（土日・祝日以外）の数です。1日8時間として、規模の実働工数（1日＝8時間・1週＝40時間・1か月＝160時間など）と比べます。無効化した担当者は数えません。
- 規模・開始日・期限・担当者・状態を変えるたびに確かめ直します。超えたまま「登録」「保存」を押すと「このまま保存しますか？」と確かめます（保存は止めません）。保存した後のタスクの画面にも同じ案内を出します（JavaScript が無効なときも）。
- 開始日・期限・規模のどれかが無いとき・開始日が期限より後のとき・期間が800日以上のとき・状態が「完了」のときは確かめません。

### メールから下書き
登録の画面にメールのファイル（Outlook の `.msg`・`.eml`。40MB まで）をドロップする（または「ファイルを選ぶ」）と、**AI が** タイトル・内容・開始日・期限・優先度・規模・必要スキルの欄に下書きを入れます。**保存はしません**（確かめて「登録」を押したときに保存します）。入力中の内容があるときは、置き換える前に確認します。Outlook の一覧から直接ドラッグできないときは、メールをファイルに保存してからドロップしてください。
- 読むのは件名・差出人・日時・宛先・CC・本文・添付のファイル名だけです（ファイルは保存せず、添付ファイルの中身も読みません）。`.msg` は追加のライブラリを使わずに読みます（本文はテキスト → HTML → RTF の順）。
- **AI**（AI が設定されていれば、いつも使います。使うかどうかを選ぶ欄はありません）: メールと有効なスキル項目の一覧・規模の選択肢を AI に送り、タイトル・内容のまとめ・開始日・期限・優先度・**規模**（依頼の内容から見積もった実働工数に近いもの）・必要スキルを作らせます。応答は項目ごとに確かめ（日付の形と範囲・優先度と規模の選択肢・スキルの番号と到達度）、使えない値は決まった読み取り方の値のままにします（規模は空）。内容は AI のまとめの後に【元のメール】を付けます。AI が見積もった規模は「規模（AI）: 1週（理由）」のように表示します（「1ヶ月」「２週」「1週間」のような書き方の違いもそろえます。選択肢に無い答えは入れずに、その旨を表示します）。AI に失敗したときは、決まった読み取り方の下書きにして理由を表示します。
- **決まった読み取り方**（AI が未設定のとき・AI に失敗したとき。AI が未設定のあいだは、画面にその旨〔admin がシステム管理の「基本設定」で AI の接続先を設定〕を表示します）: タイトル＝件名（先頭の `RE:`・`FW:` などを除く）、内容＝【元のメール】（件名・差出人・日時・宛先・CC・添付）と本文（4000文字まで）、期限＝「11/15まで」「期限：11月15日」のような書き方の日付（年の無い日付はメールの日付から決めます）、優先度＝重要度（高・低）と件名・本文の始めの「至急」「緊急」など、必要スキル＝有効なスキル項目の名前が件名・本文に出てくるもの（Lv2）。規模は入れません。

## 出勤表と勤務（シフト）

「出勤表」のタブ（以前の「年休」のタブ）は、**横軸に日付、縦軸に勤務帯・勤務と人** を並べた月ごとの表です。
- 勤務の行（緑）に勤務表の記号、その下の人の行に年休（年＝全休・前＝午前半休・後＝午後半休。枠だけの前・後＝午前時間休・午後時間休）と休みの日（灰色）を表示します。勤務の登録が無い人は「勤務の登録なし」にまとめます。最後の行は日ごとの年休の人数（半休も1人。時間休は数えません）で、同じチームで同じ日に休む人数が多い日に印を付けます。
- **時間休**（午前時間休・午後時間休。午前・午後の数時間の年休）: 時間は記録しません。換算日数（年休の一覧の合計・詳細・Excel）には数えず（一覧・詳細は「時間単位」と表示）、同じチームで同じ日に休む人数（出勤表の印・登録のときの調整のお願い）にも数えません。担当者の推奨・規模と出勤日数の確認では、出勤の日として数えます。
- 自分の行の出勤の日の「＋」から、その日の年休を登録できます。年休は、勤務表で出勤の日なら土日・祝日でも登録でき、勤務表で休日・年休の日は登録できません（勤務表の記号が無い日は、今までどおり土日・祝日は登録できません）。
- 勤務・勤務表の記号・勤務表は **会社の中で共通（すべての環境で共通）** です（メインの環境の DB に置き、admin だけがシステム管理の「勤務パターン」で変更します）。各環境の出勤表は、この勤務表と、その環境のメンバーの勤務・年休から作ります。
- **勤務の設定**（admin。システム管理の「勤務パターン」。出勤表の「勤務の設定」のボタンも admin にだけ表示）: 勤務（例: 「1班 A」「日勤」）の追加・名前・勤務帯（出勤表で行をまとめる名前。例: 「1班」）・並び順・有効/無効と、**勤務表の記号**（1文字）の名前・種類を設定します。種類は「出勤」「臨時出勤」（出勤の日として数える）・「休日」・「年休」（休み。担当者の推奨で対応できない日）です。記号が1つも無いときは例（1〜4・●・○・①〜④・□）を入れてあるので、名前を勤務表の凡例に合わせて保存します。勤務表で使っている記号は消せません。
- **勤務表の入力**（admin。システム管理の「勤務パターン」の「勤務表の入力」。出勤表の「勤務表の入力」のボタンも admin にだけ表示）: 月ごとに、勤務ごとの日の記号を入力します。Excel の勤務表の1行（日のセル）をコピーしてそのまま貼り付けられます（タブ区切り。空のセルは記号なし）。空白・「,」区切りや、区切らずに続けて入力してもかまいません。記号の無い日は「-」です。記号の一覧に無い記号・日数より多い記号があると保存しません。画面を開いた後にほかの操作で変わった勤務の行は上書きしません。
- **Excel で取り込む（年間分などまとめて）**（admin。「勤務表の入力」の画面の上）: Excel（`.xlsx`・`.xlsm`。10MB まで）の表から、何か月分でもまとめて勤務表を登録します。表は、**見出しの行に日付**（日付のセル、「2026/11/5」「11/5」の文字、または日〔1〜31〕。日だけのときはシートの名前〔「2026年11月」など〕か、見出しより上のセルの「2026年11月」で年月を決めます。どちらも無いシートが1つだけなら画面の月として読みます。月の終わりの日から1に戻ると次の月）、**その下の行の左の列に勤務の名前**（勤務の設定の名前と同じ。勤務帯と名前を別の列に分けてもかまいません）、**日の列に記号**です。空のセル・「-」は記号なし。シートはいくつあってもかまいません（1シート1か月でも、1枚に1年分の日付を横に並べた表でも）。曜日の行は読み飛ばします。
  - 「**ひな形をダウンロード**」: 開始の月から 1〜12 か月分（1シート1か月。見出しは日付のセル・曜日の行・有効な勤務の行・記号のシート）を、今の勤務表の記号を入れて作ります。記号を入れて（直して）そのまま取り込めます。
  - 取り込み: 記号の一覧に無い記号・同じ日の記号の食い違い・年月の分からないシートがあれば **何も保存しません**（場所を表示）。勤務の名前と一致しない行・日付の見出しの無いシートは読まずに案内します。**ファイルにある日だけを上書きします**（月の途中までの表なら、ほかの日は今のまま）。取り込んだ月・勤務の数は画面とサーバーのログに出します。
- 記号の無い日（未入力の月・記号なしの日・勤務の無い人）は、土日・祝日を休み、それ以外を出勤として扱います。
- **メンバーの勤務**: 各環境のチームの管理の「メンバーの管理」で選びます（その環境のマネージャー。メンバーの追加のときにも選べます）。1人1つです。勤務の設定の画面の人数は、すべての環境のメンバーの合計です。無効にした勤務は選択肢に出ません（登録済みの人はそのまま）。

## 複数の環境（グループ）

1つのサーバー（このフォルダ）を、複数のグループ（マネージャーごとのチーム）で使い分けられます。ログインの画面は1つで、ログインの後に使う環境を選びます。環境ごとに、タスク・定型業務・スキル・出勤表・チーム（メンバー）・定期メールの設定・AI分析の結果がすべて分かれます（ほかの環境のデータは見えません）。

- **メインの環境**: 今までのデータ（`instance/app.db` ほか）。URL も今までどおり（`/tasks` など）。
- **ほかの環境**: `instance/envs/<キー>/`（キーは `e2`・`e3`…）に DB（`app.db`）と設定のファイルを置きます。URL は `/env/<キー>/` の下（例: `/env/e2/tasks`）。
- 使える環境が1つ（メインだけ、またはほかの環境をすべて停止）のあいだは、ログイン・URL・画面は今までとまったく同じです。

### 環境の追加（システム管理の「環境」）
- 固定ローカル管理者（admin）だけが、システム管理の「**環境**」で追加します。**環境の名前だけ** を入力して「環境を追加」を押すと、新しい DB を作ります。続けて「開く」でその環境に入り、チーム管理でメンバー（その環境のマネージャーを含む）を登録します。
- その後のメンバーの登録は、その環境のマネージャー（または admin）がその環境の「チーム管理」で行います（今までと同じ。登録していない人はその環境に入れません）。同じ人を複数の環境に登録することもできます。
- 同じ画面で、環境の名前の変更と停止・再開ができます。停止した環境は開けなくなり（URL は 404）、環境の選択の画面にも出ず、定期メールも送りません（データは残り、再開できます）。環境の削除はできません。メインの環境は停止できません（名前は変えられます。最初の名前は「メインの環境」）。
- 環境を追加しても、ログイン中の人はそのまま使えます（次のログインから、ログインの後の環境の選択が始まります）。

### ログインと環境の選択
- ログインの画面（`/login`）は1つです。ID とパスワード（今までと同じ `ldap_client.py` の認証・失敗の制限）を確かめた後、**有効なメンバーとして登録されている環境** に進みます（1つならその環境へ直接、複数なら「環境の選択」の画面）。どの環境にも登録されていなければ、今までと同じく「このIDはアプリに登録されていません」と表示します。
- 固定ローカル管理者（`admin`）は、ログインの後にシステム管理の画面を表示し、そこからすべての環境を開けます（初めて入るときに、その環境に admin のユーザーを用意します）。
- ナビに今の環境の名前を表示し、ユーザーのメニューの「**環境の切り替え**」（admin は「**システム管理**」）で選び直せます。同じブラウザの別のタブで、別の環境を同時に開くこともできます（クッキーも環境ごと。開いたままの古いタブから保存しても、ほかの環境のデータは変わりません）。
- 環境に登録されていない人がその環境の URL を開くと、「この環境には登録されていません」と表示します（環境の選び直しのボタン付き）。
- ログアウトすると、そのブラウザのすべての環境のログインが終わります。ログインの有効期限（12時間）と、admin のパスワードの変更による再ログインも、すべての環境に効きます。メンバーを無効化・削除すると、その環境のログインだけが終わります。
- ログインの記録は、共通のログインが `instance/portal_sessions.json`、環境ごとのログインが各環境の `login_sessions.json` です（Git 管理外。DB は使いません）。

### 設定（すべての環境で共通のものと、環境ごとのもの）
- **基本設定（AI・メールの送信サーバー・ポート番号・差出人・送信を許可するドメイン・リンクの基準URL・LDAP・admin のパスワード・SECRET_KEY）は、すべての環境で共通** です（`instance/settings.json`）。変更・接続テストができるのは admin のシステム管理の「基本設定」だけです。
- **メールの宛先（`MAIL_TO`・`MAIL_CC`。週報・期限超過通知）は環境ごと** です。各環境のシステム設定の「**メールの宛先**」タブで設定します（`env_mail_settings.json`。メインの環境は `instance/`、ほかの環境は `instance/envs/<キー>/`）。メインの環境は、保存するまで以前の基本設定の宛先を使います。ほかの環境は、メインの環境の宛先・`config.py` の宛先には送りません（宛先を設定するまで送りません）。
- 週報・期限超過通知・スキル（AI）・AI分析・定型業務リマインドの設定と、メンバーのメールアドレスは環境ごとです。
- **勤務パターン（勤務・勤務表の記号・勤務表）も、すべての環境で共通** です（メインの環境の DB。admin がシステム管理の「勤務パターン」で変更）。メンバーの勤務（どの勤務か）は環境ごとです。以前の版（環境ごとに勤務を持っていた版）でほかの環境に作った勤務は使わなくなりました。新しい版で最初に起動したときに一度だけ、その環境のメンバーの勤務を、同じ名前の共通の勤務に付け替えます（同じ名前の勤務が無い人は勤務を外すので、システム管理の「勤務パターン」で勤務を作り、その環境のチーム管理で選び直してください。付け替えた人数はサーバーのログに出します）。
- 定期メールの自動送信は、1つのスケジューラがすべての環境（停止したものを除く）を確かめます。メールのリンクは、その環境の URL（`/env/<キー>/…`）になります。複数の環境のときは、メール・週報に書くアプリの名前に環境の名前を付けます（例: 「業務管理システム（〇〇グループ）」）。
- 新しい版で既存のテーブルに列が増えたとき（`flask --app app migrate`）は、ほかの環境の DB にも `flask --app app migrate --db instance/envs/<キー>/app.db` を実行します（足りないテーブルは、今までどおり起動の後に自動で作ります）。

## スキル（到達度 Lv0〜3・自動更新・AIの分析と相談）

スキル管理（マネージャーのナビの「管理」→「スキル」。マネージャーのみ）で、メンバーのスキルの到達度を管理します。

### 到達尺度（すべてのスキル共通）
| レベル | 意味 |
|------|------|
| Lv0 | 未習得 |
| Lv1 | 先輩と一緒にできる |
| Lv2 | 単独でできる（自立） |
| Lv3 | 教えることができる（自律） |

- テクニカル・コンセプチュアル・ヒューマンの3区分とも同じ尺度です。Lv2（単独でできる）以上を保有者（単独可）として数えます（スキルマップの「単独可」・マネージャーダッシュボードのスキル保有状況・AI分析の偏り）。業務に必要なスキルのレベルも同じ尺度です。
- **以前の版の値の読み替え**: 以前の版は区分ごとに尺度が違いました（テクニカル Lv0〜6、コンセプチュアル・ヒューマン Lv0〜5）。新しい版で最初に起動したときに一度だけ、メンバーの到達度（`skill_ratings`）と業務の必要レベル（`operation_skills`）を次のように読み替えます。読み替える行があるときは、先に DB の控え（`instance/app.db.bak-before-skill-scale-日時`）を作ります。読み替えたメンバーの到達度は、変更の履歴に「到達尺度の変換」として以前のレベルとともに残ります（最終更新の日時は変えません）。済んだ印を新しいテーブル `app_marks` に残すため、2回目からは行いません。

| 区分 | 以前の Lv1 | Lv2 | Lv3 | Lv4 | Lv5 | Lv6 |
|------|------|------|------|------|------|------|
| テクニカル | 1 | 2 | 2 | 2 | 3 | 3 |
| コンセプチュアル | 1 | 2 | 2 | 3 | 3 | ― |
| ヒューマン | 1 | 2 | 3 | 3 | 3 | ― |

（テクニカルは「簡単なものが作れる」→1、「少し難しいもの〜大体何でも作れる」→2、「指導できる」「勉強会を開催できる」→3。コンセプチュアルは「課題を構造化し解決策を立案できる」以上→3、ヒューマンは「後輩の相談に乗り指導できる」以上→3）

### タスクの完了からのスキルの自動更新
- タスクを「**完了**」にすると（編集画面・状態の変更のどちらでも）、そのタスクに **進捗を記載したメンバー** を対象に、AI が記載の内容から上げられるスキルを判定し、到達度を上げます。**担当者かどうかではなく、進捗の記載者とその記載の内容** で判断します（担当者でも記載が無い人は対象外、担当者でなくても記載した人は対象。マネージャー・無効化したメンバーは対象外。マネージャーの記載は状況を知る参考として読みます）。
- 判定の決まり:
  - 根拠は **本人の記載からの引用** です。AI が示した引用が本人の記載に連続してそのまま見つからない判定（空白・全角半角の違いは無視。8文字未満の引用・「…」でつないだ引用は使いません）、有効でないスキル、対象者でない人の判定は使いません。
  - **上げるだけ**（下げません）。反映する時点の到達度より上のときだけで、1回の完了で上げる段階は設定の上限（既定 1）までです（最大 Lv3）。同じタスクからは、完了を繰り返しても（記載を書き足しても）合計でこの上限までしか上げません。
  - 前回の判定と進捗の記載が同じなら判定し直しません（完了→進行中→完了 で同じ記載から上げ続けないように）。
  - AI が未設定のときは判定しません（判定の記録に「AIが未設定」と残し、設定した後に変更の履歴の「判定し直す」で判定できます）。
- 判定は別の処理で行うため、完了の操作はすぐに終わります（判定は数十秒〜数分。1件ずつ順番に行います。サーバーの停止などで30分以上「判定中」のままのものは「中断」と表示し、判定し直せます）。
- 結果は、タスクの詳細（マネージャーだけに表示）、スキルマップの「最近の自動更新」、個人のスキルの画面、**変更の履歴**（`/skills/history`。判定ごとの AI の提案と扱いも）で確認できます。スキルマップのセルと個人のスキルの画面には、今の到達度が自動更新によるものに印を付けます。
- **取り消し**: 変更の履歴・個人のスキルの画面の「取り消す」で、自動更新の前のレベルに戻せます（その自動更新がそのスキルの最新の変更で、到達度がそのままのときだけ。後からマネージャーが変えたものは取り消せません。未評価から上がったものは未評価に戻します）。
- マネージャーが到達度の編集でレベルを変えたときも、変更の履歴に記録します（メモだけの変更は記録しません）。
- 設定はシステム設定の「**スキル（AI）**」タブ: 自動で更新する/しない（既定はする）・1回の完了で上げる段階の上限（1〜3。既定 1）。保存先は `instance/skill_ai_settings.json`。
- AI の接続先に送る内容: タスクの名前・説明・成果・進捗の記載（書いた人の氏名・日時を含む）、対象者の氏名と到達度、スキル項目（説明の先頭）。記載の中の指示には従わないよう AI に伝えます。

### スキルマップの AI（分析コメント・相談・計画）
スキルマップの上部の「**AIのスキル分析・相談**」に次のタブがあります（マネージャーのみ。AI が未設定のあいだは使えません）。
- **分析コメント**: 「AIで分析」を押すと、スキルマップ（メンバーの到達度・スキル項目・業務に必要なスキルと対応できる人・最近90日の到達度の変更・保存済みの計画とメモ）を AI が読み、チームのまとめ・強み・弱み（リスク）・アクションアイテムと、メンバーごとの強み・弱み・次に伸ばすことを表示します。最新の1回分を `instance/skill_map_ai.json` に保存します（失敗したときは前の結果を残し、失敗したことを表示します）。
- **AIに相談**: 「新しい相談」でチーム全体またはメンバーを話題にした会話を作り、AI と話しながら弱み・強みの整理、アクションアイテム・中期計画・教育計画を立てます。AI には毎回、いまのスキルマップ（上と同じ材料。話題のメンバーがいれば、その人の担当タスクの名前・状態も）と直前のやり取り（20件まで）を送ります。会話は DB の新しいテーブル（`skill_chat_threads` / `skill_chat_messages`）に残り、マネージャー全員が見られます（会話は削除できます。保存した計画・メモは残ります）。
- **計画・メモ**: AI の応答の「**計画に保存**」で、種類（強み／弱み・課題／アクションアイテム／中期計画／教育計画／メモ）・対象（チーム全体またはメンバー）・期限を付けて保存し、編集・完了にできます（新しいテーブル `skill_plans`。一覧は `/skills/plans`）。進行中の計画・メモは次の分析・相談の材料にもなるため、AI と一緒に計画を育てていけます。
- **最近の自動更新**: タスクの完了からの自動更新の新しい5件と、変更の履歴へのリンク。

### スキル項目の説明
- 説明は到達度を判断するときの基準です（マネージャーの判断と、自動更新の AI の判定に使います）。おすすめの見出しは「対象範囲」「使う道具・言語・ソフト（テクニカルスキル）」「レベルごとの目安（Lv1〜Lv3）」「対象外の内容」です（以前の版の見出し「出題しない範囲」も「対象外の内容」として読みます）。「AIで下書き」はこの形の下書きを説明の欄に入れます（保存はしません）。

### スキルテストの削除
- 以前の版のスキルテスト（AI が作った4択問題の受験）は削除しました（画面・設定のタブ・Excel 出力はありません。`/skilltest/` は 404）。DB のテーブル（`skill_test_questions` / `skill_test_attempts` / `skill_test_answers`）と `instance/skilltest_settings.json` は残りますが、使いません（削除は不要です）。スキルテストで登録された到達度はそのまま残り、上の読み替えの対象になります。

## AI分析（サマリーと推奨アクション）

マネージャーダッシュボードの一番上のエグゼクティブサマリー（下の「[マネージャーダッシュボードのエグゼクティブサマリー](#マネージャーダッシュボードのエグゼクティブサマリー)」）にある「AI分析の画面」のリンク（`/manager/analysis`）から開きます。マネージャーのみ（メンバーは画面・データのどれも見られず、URL を直接開いても 403）。
チームの状況を4つの観点にまとめ、**いまマネージャーが対応すること（推奨アクション）** を優先度の高い順に示します。
数値と一覧はすべてアプリ（`app.py` の「9」）が計算します。画面を開くとすぐに表示されます。DB のテーブルは追加・変更しません（読み取りのみ）。
「**AIで分析**」を押すと、AI がタスク・コメントなどの本文を読んで判定・書き直し案・所見・推奨アクションを加えます（「[AIで分析](#aiで分析)」）。AI が未設定・失敗のときも、アプリの集計とルールによる推奨アクションはそのまま表示します。

### マネージャーダッシュボードのエグゼクティブサマリー
マネージャーダッシュボードの一番上に、AI分析の内容を **1つの文章（エグゼクティブサマリー）** にまとめて表示します（画面を切り替えずに見られます。表示だけで、問い合わせ〔チャット〕はありません。項目ごとの表・書き直し案は AI分析の画面）。
- **文章**: 対象（期間・メンバーの人数・現時点）→ 【全体の状況】（アプリの集計: タスク・マネージャーのコメント・スキル・成果・負荷）→ 【AIのまとめ】（AI の結果があるとき。①〜④ごと）→ 【いま対応すること】（AI の推奨アクション。AI の結果が無ければルールの推奨アクション。理由つき）。長いときは欄の中でスクロールします。
- **期間**: 保存されている AI の結果があればその期間（AI のまとめをそのまま出すため）、無ければ直近30日です。
- **AIで分析**: ダッシュボードの「AIで分析」は直近30日で実行し、実行中は進み具合を表示して、終わると自動で読み直します（AI が未設定なら押せません。送る内容は AI分析の画面と同じ）。
- まとめを作れなかったとき（想定外のエラー）も、ダッシュボードはその旨を出して表示します（内容はサーバーのログ）。

### 期間

- **現時点**: 期限超過・期限が近いのに未着手・記載がない・保留・負荷・スキルの分布と偏りは、今の状態です（過去の期間を選んでも、期間の後に登録されたタスクを含む今のタスクすべてが対象）。

### ① タスクの進捗
- **進み**（期間内）: 完了したタスク（最後に「完了」にした日時。状態の変更の記録が無い完了タスクは更新日時で代用し「推定」）、着手したタスク（期間内に「進行中」になった）。
- **遅れ**（現時点）: 期限超過（超過した営業日数。今日が土日祝で 0営業日のときは「0営業日（N日超過・休日）」）、期限が近いのに未着手（残りの営業日数）、進行中なのに記載がない（経過した営業日数と起点）。
- **課題**: 保留中のタスク（保留にした日からの営業日数・最後の記載）。
- **マネージャーのコメントへの対応**: 未完了のタスクと期間内に完了したタスクへのマネージャーのコメント（全期間）と、期間内に書かれたコメントが対象です（そのタスクの担当者でもあるマネージャーの記載は除く）。後に担当者のコメントが無いものを「**返信なし**」とし、書かれてからの営業日数を表示します（担当者のいないタスクは、マネージャー以外のだれかのコメントがあれば返信あり）。「了解です」「ありがとう」「ご対応ありがとうございます」「共有ありがとうございます！」「了解しました。引き続きよろしくお願いいたします。」「了解です👍」のような、了解・お礼・あいさつだけのコメント（絵文字・顔文字を含む）は「対応不要」として数から除きます（「ご対応よろしくお願いします」のような依頼は除きません）。絵文字だけのコメントは「👍」「🙏」「🙇」のような了解・お礼の絵文字だけのときに除き、質問・注意の記号（「❓」「❗」「⚠️」「🆘」「⏰」など）を含むコメントは除きません。
- 「AIで分析」の後は、返信のあるコメントについて AI がマネージャーの求めたこと（指示・質問・依頼）を読み取り、後のコメントと状態の変更から「**対応済み／一部対応／未対応**」を判定し、残っている対応と根拠（使ったコメントなど）を表示します。返信のないコメントは「返信なし」のまま（判定はアプリ）です。求めていることの無いコメント（励ましなど）は「対応不要（AI判定）」として数から除き、一覧で確認できます。
- チームの件数とヒト別の件数（複数担当のタスクは各担当に数え、チームは1件として数える）、要フォローの一覧（「返信なし」「未対応」「一部対応」。タスクへのリンク・担当・コメントと日付・判定・残っている対応・経過）。
- 「AIで分析」の後は、未完了のタスクと期間内に完了したタスクのコメントから AI が抜き出した **課題・相談**（根拠のコメント付き）も表示します（保留中のタスクには、その課題を並べて表示）。
- 判定はコメント・タスク・人の ID だけでなく、タスクの印（ID と登録日時）・コメントを書いた日時・ログインIDと一緒に保存します。分析の後にタスクやメンバーを削除し、同じ ID が別のコメント・別の人に再利用されても、前の判定・書き直し案・所見は出しません（所見は「分析の後に変更あり」）。
- 分析を始めた日時（秒まで保存します）より後に書かれた・完了した項目は「**分析の後に追加**」と表示します（同じ分のうちに後から書かれたコメントも含みます）。
- 分析の後にコメント・状態・成果などが変わった項目は「**分析の後に変更あり**」と表示し、その AI の判定・書き直し案は使いません（返信のあるコメントは「未判定」として要フォロー・推奨アクションから外し、返信のないコメントは「返信なし」のまま。課題・相談は印を付けて残す）。分析の後に担当・役割が変わって新しく対象になった項目（分析の後に担当者に加わった人の進捗の記載、マネージャーにした人のコメントなど。分析のときは AI に判定を頼んでいない）も「分析の後に変更あり」にします（「判定なし」は、判定を頼んだが AI の応答に無かったものだけ）。もう一度「AIで分析」を実行すると判定し直します。

### ③ 成果物の状況（チーム全体とヒト別）
- 期間内に完了したタスクの成果（定量の見込み・実績・単位・補足、定性の見込み・実績）をルールで確認し、「**書き直し推奨**」の一覧（理由・今の記載・タスクへのリンク）と指摘の種類ごとの件数を表示します。
  「AIで分析」の後は、AI のあいまいさの判定（「あいまい（AI判定）」）を指摘に加え、書き直し推奨の行ごとに **書き直し案**（そのタスクとコメントに書かれた事実だけ。材料に無い数値は「◯」）と「**案をコピー**」ボタンを表示します。案は自動では反映しません（タスクを開いて貼り付けます）。
  ルール: 実績が空（見込みだけ）／ 数値に単位がない ／ 定量の実績に補足（根拠・計算方法）がない ／ 実績が見込みの50%未満・200%超（年換算）／ 定性の実績が15文字未満・補足が10文字未満。
- 成果の合計（金額 ￥/年・時間 ｈ/年。マネージャーダッシュボードの成果と同じ年換算。ヒト別は複数担当を担当者の数〔無効化した人を含む〕で均等割り。チームの合計にはマネージャー・無効化した人の分も含むため、ヒト別の合計とは一致しないことがあります）。

### 推奨アクション
期限超過・マネージャーのコメントに返信なし・進行中なのに記載がない・期限が近いのに未着手・長い保留・負荷が高い（160h/月以上）・対応できる人が1名以下の業務・保有者が1名以下のスキル・成果や進捗の書き直し推奨から、優先度の高い順に最大10件を選びます（種類ごとの点数の帯の中で並べ、期限が近いのに未着手は、しきい値 N1 を大きくしても進行中なのに記載がない・返信なし・期限超過より上にはしません。同じ種類は数件まで。候補が5件に満たないときは同じ種類からも補います。1つのタスクに返信の無いマネージャーのコメントが複数あっても、そのタスクのアクションは1件にまとめます）。
担当者が全員無効化されたタスクは、担当者のいないタスクと同じく「担当者を決めて…」とし（無効化した人には頼みません）、一覧・AI に送る材料では名前に「［無効］」を付けます（AI には「担当者のいないタスク〔マネージャーだけ・無効化したメンバーだけが担当のものを含む〕」として送ります）。
各アクションには、やること・対象（タスク／ヒト／スキル／業務へのリンク）・理由・根拠の数値を付けます。理由・数値の日付（期限・最後の進捗記載・コメントの日付）は `mm/dd` で、分析の基準の日時と違う年のものは `yyyy/mm/dd` で書きます（AI に送る候補・チームのまとめの材料と、画面の表〔期限超過・未完了・保留の最後の記載、マネージャーのコメント、書き直し推奨の記載、課題・相談の出どころ〕のコメントの日付も同じ）。
「AIで分析」の後は、AI が材料とこの候補をもとに選んだ推奨アクション（5〜10件）を表示します（ルールで選んだものは折りたたんで表示）。分析の後に対象のタスクが変わった（完了した・コメントに返信が来た・期限や担当者が変わったなど）推奨アクションには「**分析の後に変更あり**」を付け、リンクにしません。AI の推奨アクションの対象は候補か実在するタスク・ヒト・スキル・業務だけで、根拠の数値は材料にある数値だけです（5件に満たないときはルールの候補で補います）。AI が未設定・失敗のときは、ルールで選んだものを表示します。

### AIで分析
画面上部の「**AIで分析**」を押すと、表示している期間で AI による分析を別のスレッドで始めます（画面はすぐに戻り、実行中は進み具合を表示。終わると画面が自動で更新されます。同時に1つだけ）。AI の接続先は、週報などと同じくシステム管理の「基本設定」の `AI_API_URL` / `AI_API_KEY` / `AI_MODEL` です（未設定ならボタンは使えません）。

- **送る内容**: タスクの名前・説明・すべてのコメント（書いた人の氏名・日時）・状態の変更・成果（完了したタスクの記載と、未完了のタスクの途中の記載・見込み。長い欄も省略しない）、メンバーの氏名、スキルの分布と偏り（保有しているスキルはすべて）、期間内のスキルの更新（理由・きっかけのタスクの名前を含む）。画面にもこの注意を表示します。件数などの数値はアプリが計算して「【数値】」として渡し、AI には計算・創作させません（応答に材料に無い数値があれば「◯」に置き換え、画面に出す文で置き換えた数を表示します。件数・時間などの数量は材料の本文・数値にあるものだけを認め、登録・期限・コメントの日時や T12 のような ID の数字は数量として認めません。日付・時刻は材料にあるものだけ〔「10月」「2026/10」のような月・年月は、材料の日付にある月・年月なら認めます。「3/5」のような分数は、材料の日付に無くても数値がすべて材料にあれば認めます。材料の本文に「12/20 件」「3/5 ページ」「9/10」「1:30」のように「/」「:」で区切って書かれた2つの数は、日付・時刻とも分数・件数・所要時間とも読めるため、数量としても認めます〔「20件中12件」「1時間30分」のような言い換えを「◯」にしない〕。年月日の3つの数〔2026/10/02〕・「10月2日」・見出しの日時と、日付に続けて書いた時刻〔「2026/10/01 17:45」「10/01 17:45」。コメントの日時など〕は日付・時刻としてだけ認めます。各人・所見・チームのまとめでは、「/」「:」で区切った2つの数を数量としても認めるのは、タスク・コメント・成果の本文とアプリが計算した数値〔「目安超過 3/5件」など〕にも同じ数が書かれているときだけです〔推奨アクションの候補・要フォローのコメントの日付「期限（10/13）」「09/15」や、AI が書いた所見・分かったこと・要約にだけある「10/01」などは日付としてだけ認めます〕〕）。タスク・コメントの本文はデータとして渡し、本文の中の指示には従わないよう AI に伝えます（本文の中の「■」「【】」などの見出しの記号は別の記号に置き換えて送ります。チームのまとめの材料に入れる AI の文〔所見・分かったこと・スキルのまとめ・要約の要点〕も、同じく記号を置き換えて1行にします）。
- **送る順**: ①メンバーごと（その人に関係するタスク〔未完了のもの・期間内に完了や動きがあったもの〕の全文とその人の数値）→ 担当者のいないタスク → ②スキル → ③チームのまとめ（観点ごとのまとめと推奨アクション）。1人分が「1回に送る材料の最大文字数」より長いときは、タスクのまとまりごとに分けて送り、最後にその人の所見だけを作る呼び出しを1回加えます（長いタスク・コメント・成果の欄も途中で分けて送り、省略しません）。1件のタスクを分けて送るときは、状態の変更を毎回の見出しに付け、マネージャーのコメントへの対応と成果の判定はそのタスクの最後の回で頼みます（それより前の回で AI がまとめた経過メモ・成果の事実メモと、前の回で送ったマネージャーのコメントの本文を最後の回に渡します〔1回に送る文字数に入りきるときは全文、入りきらないときは先頭の約200文字、それも入らないときは本文を省いて AI の経過メモだけ（メモも短くすることがあります）〕。前の回が失敗したタスクの判定は頼まず「未読込」）。長いコメントの本文を分けて送るときは、進捗記載の判定はその記載の最後の部分を送る回だけで頼み、前の回で送った部分（マネージャーのコメントは経過メモも）を【前の回までに分かったこと】で渡します（共同担当のタスクで、判定を頼む単位がほかの担当者のときの、その人の進捗記載も同じ）。その記載の前の部分を送った回が失敗したときは判定を頼まず「未読込」にします（同じタスクのほかの部分〔説明など〕の回だけが失敗したときは、その記載の判定は頼みます）。AI が書いた経過メモ・成果の事実メモ・所見の材料を次の依頼に入れるときは、利用者の本文と同じく記号（■【】[] など）を置き換えて1行にします。チームのまとめの材料が「1回に送る材料の最大文字数」より長いときは、要フォローのコメント・課題・保留・各人の数値と所見の一覧を先に分けて要約し、件数・要約・推奨アクションの候補（入りきる数まで。残りは件数）を送ります。
- **応答の確認**: 応答は JSON として読み、判定を頼んだ項目の ID・選択肢・長さを確かめます。JSON として読めないとき（入れ子が深すぎる JSON を含む）は1回だけ頼み直します。
- **読めなかったもの**: 呼び出しが失敗した材料は「**未読込: ○件**」（タスクの件数と、スキル・チームのまとめなどの回数）として内訳と理由を表示し、残りはそのまま続けます（項目ごとにも「未読込」と表示。進捗の記載は書いた人の回、マネージャーのコメント・成果はタスクの持ち主の回が読めなかったときだけ「未読込」とし、複数担当のタスクでほかの担当者の回だけが失敗したときは「判定なし」にします。読んだ・読めなかったコメントの数は、複数担当のタスクで2回送っても1件として数えます）。3回続けて失敗したときは残りを中止し、結果の上に「途中で中止しました（残り N 回の呼び出しは行っていません）」と表示します（行わなかった呼び出しは1件の「未読込」にまとめ、その回数を表示します。分けて送った材料がすべて失敗・中止になったメンバーの所見の呼び出しも、中止の後なら行わなかった呼び出しに含めます。「未読込: ○件」には行わなかったスキル・チームのまとめなどの回数も含め、「読み込めなかった呼び出し」の回数は失敗した回数と行わなかった回数の合計です。同じ期間の結果が保存済みのときは、途中までの結果で上書きせず、前の結果を残します）。1回の呼び出しが `AI_TIMEOUT`（秒）を超えると失敗になるため、メンバー・タスクが多いときは `AI_TIMEOUT` を長くするか、「1回に送る材料の最大文字数」を小さくします。1回も成功しなかったときは保存せず、前の結果を残して失敗の理由を表示します。チームのまとめが失敗したときは、ルールの推奨アクションを表示します（推奨アクションの候補が無く、AI も「無し」と答えたときは失敗とはしません）。
- **保存**: 結果は `instance/ai_analysis.json` に最新の1回分だけを上書きで保存します（作成した日時・期間・モデル名・呼び出しの成否、判定ごとに使った材料の指紋〔分析の後の変更を見つけるため〕を含む。APIキー・接続先の URL は保存しません。DB には保存しません）。画面は、表示している期間と結果の期間（開始日・終了日）が同じときに結果を反映し、違うときは「その期間で表示」のリンクを出します。メンバーは画面・実行・状態・結果のどれにもアクセスできません。

## データベース

- **SQLite3**（`instance/app.db`。`instance/` は Git 管理外）。起動時（`flask --app app run` / `seed` / `migrate`）に、足りないテーブルを `db.create_all()` で自動作成します。

  - 新しい版で最初に起動したとき、スキルの到達度と業務の必要レベルを Lv0〜3 に一度だけ読み替えます（「[スキル](#スキル到達度-lv03自動更新aiの分析と相談)」。読み替える前に DB の控えを作ります）。
- タスクの必要スキル（`task_skills`）と、勤務・勤務表（`work_shifts` / `user_shifts` / `work_shift_months` / `work_shift_codes`）も新しいテーブルで、既存の DB でも起動時に自動で追加されます（`tasks` / `users` / `leave_requests` などの既存のテーブル・列は変更しません。メンバーの勤務は `users` ではなく `user_shifts` に持ちます）。勤務・勤務表の記号・勤務表（`work_shifts` / `work_shift_months` / `work_shift_codes`）はメインの環境の DB（`instance/app.db`）の表を、すべての環境で共通に使います（メンバーの勤務の `user_shifts` は環境ごとの DB）。
- 以前の版のスキルテストのテーブル（`skill_test_questions` / `skill_test_attempts` / `skill_test_answers`）は DB に残りますが、現在のコードからは使用しません（削除は不要です）。
- 定型業務のリマインドのテーブル（`user_emails` / `routine_reminders` / `routine_occurrences` / `routine_reminder_email_checks`）も新しいテーブルで、既存の DB でも起動時に自動で追加されます（`users` / `routine_works` などの既存のテーブル・列は変更しません）。
- 以前の「報告書」機能のテーブル（`reports` / `report_tasks` / `report_templates` / `ai_settings`）は DB に残りますが、現在のコードからは使用しません（削除は不要です）。
- **既存テーブルへの列の追加** は `db.create_all()` では反映されません。コードを新しくしたあとは、データを残したまま `flask --app app migrate` を1回実行すると、不足している列を `ALTER TABLE ... ADD COLUMN` で追加します（既存のデータは削除・変更しません。何度実行しても安全）。
  - 足りないテーブルも `migrate` で作成し、「作成されたテーブル」として名前を表示します。
  - `--check` を付けると確認だけ行い、DB を変更しません（不足しているテーブル・列を表示するだけで、テーブルも作りません）。`--db パス` で `instance/app.db` 以外の既にある DB ファイル（バックアップのコピーなど）を対象にできます（そのとき `instance/app.db` には触れません。パスを間違えたとき・SQLite の DB ではないファイルを指定したときはエラーで止まり、新しい DB は作らず、ファイルも変更しません）。
  - SQLite の制約により、NOT NULL の列は自動では追加できません（「★手動対応が必要」と表示）。DB にだけ残っている使われない列は、そのまま残します（参考として表示）。
- まっさらに作り直す場合だけ、`instance/app.db` を削除してから `flask --app app seed` を実行します。
- **複数の環境** では、ほかの環境の DB は `instance/envs/<キー>/app.db` です（環境を追加したときに作り、テーブルは今までと同じ）。環境の一覧は `instance/environments.json`、共通のログインの記録は `instance/portal_sessions.json` です（どちらも Git 管理外。既存の DB は変えません）。

## 以前の版からの更新

`app/` フォルダと `serve.py` などのスクリプトに分かれていた版から更新する手順です（ファイルをコピーして配置している場合）。

1. サーバーを止めます（自動起動のタスクがあれば、そのタスクも止めます）。
2. 念のため `instance/` フォルダ（DB・設定ファイル）をコピーしておきます。
3. 新しいファイル（`app.py` / `config.py`〔環境ごとの設定の初期値。`app.py` と同じフォルダに置く。無いと起動しません。実際の値は書かない〕/ `templates.html` / `ldap_client.py` / `README.md` / `requirements.txt` / `.gitignore`）を配置します。
4. **古いファイルを削除します**: `app/` フォルダ全体、`serve.py`、`run.py`、`seed.py`、`migrate.py`、`config.example.py`。
   - `app/` フォルダが残っていると、`flask --app app` は `app.py` ではなく古い `app/` フォルダのコードを読み込みます（Python は同じ名前のフォルダを優先するため）。Git で更新した場合は、`app/` に `__pycache__` だけが残ることがあります（読み込まれませんが、削除してかまいません）。
   - `ldap_client.py` の場所は `app/auth/ldap_client.py` からプロジェクト直下に変わりました。サーバーで本番用に書き換えた `app/auth/ldap_client.py` を使っている場合は、`app/` を消す前に、そのファイルをプロジェクト直下の `ldap_client.py` として置いてください（中身の変更は不要です）。
5. `instance/`（`app.db`・`*.json`）はそのまま使います。既存のテーブル・列は変わっていないため、`migrate` は不要です（定型業務のリマインドの新しいテーブルは、起動時に自動で作成されます。`flask --app app migrate --check` で確認できます）。
   - **`instance/config.py` はもう読みません**（環境ごとの設定は、同梱の `config.py`〔初期値〕とシステム管理の基本設定の画面〔`instance/settings.json`〕の2つの層になりました。「[設定](#設定初期値-configpy-と画面の設定-instancesettingsjson)」）。旧版の `instance/config.py` の値を使い続けるには、サーバーを起動する前に **`flask --app app import-old-config`** を1回実行します（`--path パス` で別の場所のファイルも指定できます）。旧版のファイルは読むだけで変更せず、値があって同梱の `config.py` と違う項目（`SECRET_KEY`・`ADMIN_PASSWORD`・メールの設定など）を `instance/settings.json` に取り込みます（取り込んだ項目の名前だけを表示し、値は表示しません）。旧版の `AI_API_URL` が空だった設定（外部の既定の接続先に送る形の設定）の `AI_API_URL` / `AI_API_KEY` / `AI_MODEL` は取り込みません（接続先を決めたうえで、画面で設定し直してください）。旧版の `AI_API_URL` を取り込むとき、旧版の `AI_API_KEY` が空で同梱の `config.py` に `AI_API_KEY` が書かれている場合は、`config.py` のキーを旧版の接続先に送らないよう `AI_API_KEY` の画面の設定を空にします（旧版と同じくキー無しで送ります。接続先が `config.py` と同じホスト・ポート・http/https ならそのままです）。項目の種類に合わない型の値（文字列でない `MAIL_FROM` など）も取り込みません。基本設定の項目でないもの（使わなくなった項目・`APP_NAME` などの固定設定の上書き）も取り込みません（必要なら同梱の `config.py` に直接書きます）。取り込まずに起動すると、起動時に「旧版の instance/config.py があります。flask --app app import-old-config で取り込めます」と表示します（admin のパスワードが空のため、同梱の `ldap_client.py` の固定パスワードで `admin` がログインできる状態になります）。取り込みが済んだ `instance/config.py` は残しておいても読まれませんが、パスワード・キーが書かれているので削除するか安全な場所に移してください。
6. 自動起動（タスク スケジューラなど）で `python serve.py` や `waitress-serve ... --call app:create_app` を実行していた場合は、`flask --app app run --host 0.0.0.0 --port 8050` に置き換えます（「[サーバーの起動時に自動で起動する](#サーバーの起動時に自動で起動する)」）。
   - 待ち受けのアドレス・ポートは旧版の `instance/config.py` の `SERVER_HOST` / `SERVER_PORT` ではなく、`--host` / `--port` で指定します。以前と同じ URL で使うには、以前の値（既定は `0.0.0.0` / `8050`）を指定してください。ポートを変える場合は `APP_BASE_URL` も合わせて変更します。
   - `waitress` は使わなくなりました（入れたままでもかまいません。不要なら `pip uninstall waitress`）。追加で必要になったパッケージはありません。
7. 以前の版の **`.env` が残っている場合は、別の場所へ移すか削除してください**。`flask` コマンドは、python-dotenv が入っていると、今いるフォルダ（またはその上のフォルダ）の `.env` を自動で読み込んで環境変数にします。アプリ（`app.py`）は環境変数を読みませんが、`FLASK_` で始まる値は `flask run` の動き（デバッグモード・ポートなど）を変え、`ldap_client.py` が環境変数を読む実装なら（同梱のダミー実装は `admin` のパスワードに `ADMIN_PASSWORD` を使用）その値も使われてしまいます。python-dotenv が入っていない場合は読み込まれず、起動時に `Tip: There are .env files present. ...` と表示されます。
8. `flask --app app run --host 0.0.0.0 --port 8050` で起動し、ログインできること、起動時に自動送信のスケジューラの起動が表示されることを確かめます。

## 開発者向けメモ

### ファイルの分け方
- `app.py`: Python のコードすべて。先頭の説明に、起動のコマンド・ほかのコマンド・動作確認で差し替える関数・**目次** があります。章は「`# ####`」、節は「`# ====`」の見出しで始まります（例: 「3. モデル」「5-3. タスク」「12-1. スケジューラ」）。
- `templates.html`: 画面テンプレート・CSS・JavaScript を、ファイルごとのセクションにまとめたものです。`{#=== tasks/list.html ===#}` のように名前だけを書いた行から、次の区切りの行の前までがそのファイルの中身です。
  - 区切りの名前がテンプレート名です（`render_template`・`include`・`extends` で指定する名前）。
  - 名前が `static/` で始まるセクションは静的ファイルで、`/static/` の後ろに残りの名前を付けた URL で配信します（例: `static/css/style.css` → `url_for('static', filename='css/style.css')`）。
  - 名前の重複・中身が空のセクションは、起動時にエラーになります。区切りの行の前後に空行を足すと、その空行も中身になります。
  - 静的ファイルは、`templates.html` を保存すると次の表示から新しい内容になります。画面テンプレートは `--debug` のときは次の表示から、それ以外はサーバーの再起動で反映されます。
- `ldap_client.py`: LDAP 認証。本番環境ごとに差し替えるファイルです（「[本番LDAPへの移行](#本番ldapへの移行)」）。

### 新しい機能の追加手順
1. `app.py` の「3. モデル」にモデルのクラスを追加します（新しいテーブルは起動時に自動作成。既存のテーブルへの列の追加は `flask --app app migrate`）。
2. 画面の Blueprint を作り（「5. 画面」の節が参考になります）、「13-2」の `BLUEPRINTS` に追加します。1つのファイルなので、関数名はファイル全体で重複しないようにします。ほかの画面と同じ名前のエンドポイントにしたいときは、関数名を変えて `endpoint=` で指定します（例: `@tasks_bp.route("/<int:task_id>", endpoint="detail")` の関数は `task_detail`）。
3. `templates.html` に `<機能名>/<画面名>.html` のセクションを追加し、`base.html` のセクションのナビにリンクを追加します。
4. `app.py` 先頭の目次と `templates.html` 先頭の目次に、追加した章・節・セクションを書き足します。

共通の部品（`app.py` の「2. 共通の部品」）:
- マネージャーだけの画面: Blueprint 全体なら `xxx_bp.before_request(managers_only)`、画面ごとなら `@manager_required`（「2-5」。未ログインはログイン画面へ、メンバーは 403）。
- 画面で編集する設定（`instance/*.json`）: 既定値（辞書）と「(項目, 検証関数)」の表（表に書けない項目があれば仕上げの関数）を決めて `JsonSettings`（「2-3」）を1つ作ります（画面から保存できる項目は既定値の `last_result` 以外。読み込み・保存・前回の結果の記録・ロック・壊れたファイルを上書きしない動きは共通）。
- 時間のかかる処理（メール送信・AI の呼び出しなど）: `start_in_thread()`（「2-6」）で、処理ごとのロックを使って別スレッドで実行します（同時に1つだけ）。
- 設定・前回の結果・画面を持つメール機能（週報・期限超過通知・定型業務リマインド）: 送信を同時に1つにする `MailJob`（「2-6」）と、画面の共通の表示・送信の開始の応答・旧URLの転送・メールのリンク（「2-7」）。
- 主キーで行を取り出すときは `get_or_404()`、フォームの数字は `form_int()`（「2-2」）。AI の応答の JSON は `parse_json_reply()`（「4-1」）で読みます。

### 環境ごとの設定の項目の追加
`app.py` の `ENV_KEYS` と `Config`（「1-1」。空の値だけ）、同梱の `config.py`（初期値。説明のコメントも）、`FIELDS`（「11-1」）の項目の定義（グループ・表示名・説明・種類・再起動の要否・秘密かどうか）の4か所に追加します（`FIELDS` と `ENV_KEYS` が一致しないと起動時に止まります）。コードの中に既定値を書かず（「入力が無ければ○○を使う」はしない）、無いときは「未設定」として扱う動きにします。値は使うたびに `current_app.config` から読むようにすると、画面で保存したときにすぐ反映されます（起動時にしか読まない項目は `restart_required=True`）。環境変数（`os.environ`）や `.env` は使いません。

### ChatGPT-API（AI整形）の設定・移行
接続情報は基本設定の `AI_API_URL` / `AI_API_KEY` / `AI_MODEL` / `AI_TIMEOUT`（システム管理の「基本設定」〔admin〕。初期値は `config.py`）です。キーは画面の設定（`instance/settings.json`。Git 管理外）に保存し、`config.py` には書かないため、リポジトリに入ることはありません。**既定の接続先・既定のモデル名はコードにありません**（アプリが自分で外部の AI の接続先を選ぶことは無く、設定した接続先にだけ送ります）。接続先がリダイレクトを返したときは、キーを別の接続先へ送らないよう、従わずにエラーにします（`AI_API_URL` には転送されない最終の URL を書きます）。システム管理の「基本設定」で変更すると保存と同時に反映され、「AI接続テスト」で確認できます（`config.py` を直接編集した場合はサーバーの再起動が必要）。AI は週報の文章整形・スキルの説明の下書き（「AIで下書き」）・AI分析・スキルの自動更新・スキルマップの AI（分析・相談）・メールからのタスクの下書き（メールの件名・本文・差出人・宛先・添付のファイル名とスキル項目の一覧・規模の選択肢を送ります）に使います（AI分析・スキルの自動更新では、メンバーの名前・タスクの内容・進捗の記載をこの接続先に送ります）。`AI_API_URL`（http/https の URL）・`AI_MODEL`・`AI_TIMEOUT`（1以上の整数）のどれかが無いあいだは機能は無効になり、どこにも接続せず、週報はルールベースの文章のみ、「AIで下書き」・スキルの自動更新・スキルマップの AI は使えず、AI分析はアプリの集計とルールの推奨アクションだけを表示します（各画面に「AIの接続先（AI_API_URL）とモデル名（AI_MODEL）をシステム管理の「基本設定」（admin）で設定してください」と表示）。
OpenAI互換の形式のエンドポイントなら `AI_API_URL` をそのURLにするだけで使えます。送る内容は `POST`、ヘッダー `Content-Type: application/json` と `Authorization: Bearer <AI_API_KEY>`（キーが空なら付けません）、本文 `{"model": AI_MODEL, "messages": [{"role": ..., "content": ...}, ...], "temperature": 0.3}` で、応答の `choices[0].message.content` を読みます。接続先が https のときは、**接続先の証明書を確認しません**（Python の requests の `verify=False` と同じです。公的でない認証局・自己署名の証明書を使う接続先でも、証明書を登録せずに URL とキーだけで使えます。証明書を確認すると、Python の知らない発行元の証明書は `[SSL: CERTIFICATE_VERIFY_FAILED] … (_ssl.c:…)` で接続できないためです）。そのため接続先が本物かどうかは確かめないので、信頼できるネットワークの中の接続先に使ってください。安全な再ネゴシエーションに対応していない古いサーバー・中継装置にも接続します（OpenSSL 3 を使う Python の `UNSAFE_LEGACY_RENEGOTIATION_DISABLED` を避けるため）。仕様が異なる場合は、**`app.py` の `_call_chat_api()`（「4-1」）の中身だけ** を書き換えてください（メッセージ列を受け取り、応答の本文を返す関数です。呼び出し側は `ai_chat()` の戻り値 `(本文, エラー)` にしか依存していないため、他のコードは変更不要）。

### 定期メールの追加
メール送信は `send_mail()`（「4-2」。テキスト版・HTML版・添付ファイル・宛先の指定に対応）、営業日の判定は `is_business_day()` など（「2-4」）を使います。
自動送信は「12-1」の `JOBS` にジョブ（設定の読み込み・実行時刻の判定・実行・失敗の記録）を追加します（週報・期限超過通知・定型業務リマインドの3つがあります。スケジューラのスレッドは1本で、ジョブごとに実行済みの記録と例外処理を持ちます。動くのは `flask --app app run` のときだけ）。

### 動作確認で差し替える関数（app._now / app._call_chat_api）
次の2つは、呼び出すたびにモジュール `app`（`app.py`）から探すため、モジュールの属性を置き換えるだけで差し替えられます。
- `app._now()`: AI分析の基準の日時（「現時点」・期間の終わり）、定型業務のリマインドの「今日」（画面の未完了の回・完了の入力の日時・テスト送信。自動送信はスケジューラの時刻）はすべてここから取ります。差し替えると、AI分析の営業日数などを、時刻を固定して確かめられます。
- `app._call_chat_api(messages)`: AI の呼び出し。差し替えると、AI に接続せずに週報の整形・問題の作成・AI分析を確かめられます（`AI_API_URL`・`AI_MODEL`・`AI_TIMEOUT` が揃っていないと AI を使わない動きになり、この関数は呼ばれないため、値を入れておきます）。

```python
from datetime import datetime

import app                                   # app.py（モジュール）

flask_app = app.create_app()                 # app.py と同じフォルダの config.py と instance/ を使う
flask_app.config.update(AI_API_URL="http://ai.example.test/v1/chat/completions", AI_MODEL="test")  # AI を「設定あり」にする
# (_call_chat_api が呼ばれるように。AI_TIMEOUT は同梱の config.py の 60)
app._now = lambda: datetime(2026, 10, 5, 9, 0)
app._call_chat_api = lambda messages: "（AIの応答の本文）"
```
`create_app()` は `app.py` と同じフォルダの `config.py` と `instance/`（本物の DB・画面の設定）を使うため、動作確認はプロジェクトのコピーで行ってください。`import app` だけでは `instance/` は作られず、自動送信も動きません。

### 本番LDAPへの移行
プロジェクト直下の `ldap_client.py` の `authenticate()` 内「LDAP-API」ブロックのみを実 API 呼び出しに置き換えます。戻り値の形（`username / display_name / role / source`）は変更しないでください。固定ローカル管理者（`_LOCAL_ACCOUNTS`）とアプリ登録チェックはそのまま残します。
- アプリ側が `ldap_client.py` から使うのは `authenticate()` と `_LOCAL_ACCOUNTS`（`admin` の表示名・役割。`flask --app app seed` では `_DUMMY_USERS` も使用）だけです。本番用に作った `ldap_client.py` はそのまま置き換えて使えます（`_DUMMY_USERS` が無い場合、`seed` は `_LOCAL_ACCOUNTS` のユーザーだけを登録し、動作確認用のユーザーを使うサンプルデータは作りません）。
- `ldap_client.py` の `from app.models.user import ROLE_MANAGER, ROLE_MEMBER` は、`app.py` がこの名前でも読めるようにしているため、書き換えずにそのまま動きます。
- `ldap_client.py` は最初のログインのときに読み込まれ、その後は読み直しません。差し替えたらサーバーを再起動してください。
